# 프로그램 구조 설계 근거

이 문서는 `ai-banking-transfer-agent`가 현재와 같은 디렉토리 구조와 프로그램 구조를 갖게 된 이유를 정량적 근거, 코드 근거, 최신 LangGraph 공식 문서 패턴을 기준으로 설명합니다.

## 1. 현재 구조 요약

현재 프로젝트는 크게 웹 계층, agent 계층, 도메인 service 계층, DB model 계층, 테스트 계층으로 나뉩니다.

```text
src/
├── agents/
│   ├── supervisor/     # Leader Agent: planning, routing, response aggregation
│   ├── subagents/      # transfer, inquiry, recommend, security
│   ├── common/         # parsing, schemas, tracing, LLM helper, services
│   ├── common/services # 순수 도메인 서비스: 이체, 잔액, 추천, 보안 rule 등
│   ├── a2a/            # Agent Card, A2A discovery metadata
│   ├── context.py      # Runtime context schema
│   └── state.py        # LangGraph state schema and reducers
├── models/             # SQLAlchemy ORM
└── web/routes/         # Flask route, page/API boundary
```

정량 기준으로 보면 다음과 같습니다.

| 항목 | 현재 수치 | 구조적 의미 |
|---|---:|---|
| `src` Python 파일 | 39개 | 기능을 단일 파일에 몰지 않고 책임 단위로 분리 |
| Sub-Agent 파일 | 4개 | `transfer`, `inquiry`, `recommend`, `security` 독립 구현 |
| Web route 파일 | 8개 | 화면/API별 Flask route 분리 |
| Domain service 파일 | 6개 | DB를 사용하는 업무 규칙을 agent node에서 분리 |
| Test Python 파일 | 5개 | parsing, transfer service, agent flow 단위 검증 |
| 주요 테스트 케이스 | 30개 이상 | planning, multi-turn, OTP, alias memory, security collaboration 검증 |

즉 이 구조는 단순히 폴더를 예쁘게 나눈 것이 아니라, 금융 이체 agent의 위험한 실행 경로와 읽기 전용 경로를 분리하고, 테스트 가능한 단위로 쪼개기 위한 구조입니다.

## 2. 최신 LangGraph 애플리케이션 구조와의 대응

LangGraph 공식 문서의 애플리케이션 구조 예시는 graph logic, state definition, tools/utilities, dependency file, env file을 분리하는 방식을 제안합니다.

공식 문서 예시에서는 다음과 같은 형태를 보여줍니다.

```text
my-app/
├── my_agent/
│   ├── utils/
│   │   ├── tools.py
│   │   ├── nodes.py
│   │   └── state.py
│   └── agent.py
├── .env
├── requirements.txt
└── langgraph.json
```

출처: LangGraph 공식 문서, Application structure  
https://docs.langchain.com/oss/python/langgraph/application-structure

이 프로젝트는 Flask 웹앱과 DB 모델이 포함되어 있으므로 공식 예시보다 더 큰 구조입니다. 하지만 핵심 매핑은 동일합니다.

| LangGraph 공식 예시 | 이 프로젝트 |
|---|---|
| `state.py` | `src/agents/state.py` |
| `agent.py` 또는 graph 생성 파일 | `src/agents/supervisor/graph.py` |
| `nodes.py` | `src/agents/subagents/*.py`, `src/agents/supervisor/graph.py` |
| `tools.py`/`utils` | `src/agents/common/services/*.py`, `src/agents/common/*.py` |
| dependency file | `requirements.txt` |
| `.env` | `.env.example`, runtime config |

따라서 현재 구조는 최신 LangGraph 예시의 "작은 graph app" 구조를 금융 agent 데모에 맞게 확장한 형태입니다.

## 3. Supervisor/Sub-Agent 구조를 쓴 이유

이 프로젝트는 사용자의 자연어 요청을 바로 실행하지 않고, Supervisor가 먼저 `ExecutionPlan`을 만들고, 하위 agent에 작업을 위임합니다.

코드 근거:

- `src/agents/supervisor/graph.py`는 `StateGraph(BankingState, context_schema=BankingContext)`를 만들고 `plan`, `transfer`, `inquiry`, `recommend`, `security`, `respond` 노드를 등록합니다.
- `route_plan()`은 `ExecutionPlan.steps`를 읽어 각 step을 `Send(step["agent"], ...)`로 fan-out합니다.
- `src/agents/common/schemas.py`에는 `PlanStep`, `ExecutionPlan`이 Pydantic schema로 정의되어 있습니다.

이 구조를 쓴 이유는 다음과 같습니다.

1. 이체, 조회, 추천, 보안은 서로 다른 위험도와 실행 방식을 가집니다.
2. Supervisor는 "어떤 agent를 부를지"만 결정하고, 실제 업무 로직은 각 Sub-Agent가 담당합니다.
3. `inquiry`와 `recommend`는 읽기 전용이라 병렬 실행할 수 있지만, `transfer`는 확인/OTP/DB 변경이 있어 단독 workflow로 제한해야 합니다.
4. 신규 agent를 추가할 때 리더 구조를 유지한 채 subgraph, planner mapping, Agent Card만 추가하면 됩니다.

LangGraph 공식 subgraph 문서도 multi-agent system과 독립 개발을 subgraph 사용 이유로 제시합니다. 특히 parent graph와 subgraph가 shared state key를 사용할 경우 compiled subgraph를 parent graph의 node로 직접 추가할 수 있다고 설명합니다.  
출처: https://docs.langchain.com/oss/python/langgraph/use-subgraphs

이 프로젝트가 정확히 이 패턴을 사용합니다.

```python
g.add_node("transfer", build_transfer_subgraph())
g.add_node("inquiry", build_inquiry_subgraph())
g.add_node("recommend", build_recommend_subgraph())
g.add_node("security", build_security_subgraph())
```

## 4. Workflow 구조를 쓴 이유

금융 이체는 일반 챗봇 답변과 달리 순서가 중요합니다.

```text
사용자 요청
→ 수신자/금액 추출
→ 수신자 해석
→ 금액/잔액/한도 검증
→ SecurityAgent 리스크 평가
→ 사용자 확인
→ OTP 필요 시 검증
→ DB 이체 실행
→ 결과 응답
```

이 흐름을 자유형 agent loop에 맡기면 재현성과 감사 가능성이 떨어집니다. 그래서 `TransferAgent`는 `extract`, `resolve`, `clarify`, `ask_amount`, `validate_and_secure`, `confirm`, `otp`, `execute`, `compose` node로 쪼개져 있습니다.

코드 근거:

- `src/agents/subagents/transfer.py`의 `build_transfer_subgraph()`는 9개 node를 명시적으로 등록합니다.
- 각 node는 `Command(goto=...)`로 다음 node를 동적으로 선택합니다.
- 확인, 금액 되묻기, OTP는 `interrupt()`로 멈춥니다.

LangGraph 공식 interrupt 문서는 `interrupt()`가 실행을 특정 지점에서 멈추고 외부 입력을 기다리는 human-in-the-loop 패턴을 지원한다고 설명합니다. 또한 resume 시 `Command(resume=...)`을 사용하고, state 저장을 위해 checkpointer와 `thread_id`가 필요하다고 설명합니다.  
출처: https://docs.langchain.com/oss/python/langgraph/interrupts

이 프로젝트의 `run_banking_agent()`도 같은 방식입니다.

```python
config = {"configurable": {"thread_id": f"{user_id}:{session_id}"}}

if has_pending:
    graph_input = Command(resume=message)
else:
    graph_input = fresh_turn_state(user_id, session_id, message)
```

## 5. Runtime Context를 분리한 이유

LangGraph 공식 Graph API 문서는 `context_schema`를 "graph state가 아닌 정보를 node에 전달하기 위한 runtime context"로 설명합니다. 예시로 model name이나 DB connection 같은 dependency 전달을 듭니다.  
출처: https://docs.langchain.com/oss/python/langgraph/graph-api

이 프로젝트는 같은 원칙을 따릅니다.

State에 들어가는 값:

- 현재 메시지
- 의도
- 수신자 alias
- 금액
- pending transfer data
- risk assessment
- agent 결과
- 응답 타입

Context에 들어가는 값:

- user_id
- session_id
- display_name
- age
- customer_tier
- risk_profile
- llm_provider
- otp_threshold
- interbank_fee

분리 이유는 명확합니다.

1. State는 그래프 진행 중 바뀌고 checkpoint에 저장되어야 합니다.
2. Context는 이번 실행 동안 고정된 환경값입니다.
3. agent node가 Flask `current_app`에 직접 의존하지 않게 됩니다.
4. 테스트에서 사용자 profile, LLM mode, OTP threshold를 쉽게 주입할 수 있습니다.

코드 근거:

```python
g = StateGraph(BankingState, context_schema=BankingContext)
```

```python
def plan_node(state: dict, runtime: Runtime[BankingContext]) -> dict:
    ctx = runtime.context
```

이 구조 덕분에 `A2A`, Flask route, test가 같은 agent graph를 서로 다른 context로 호출할 수 있습니다.

## 6. Send 병렬 fan-out 구조를 쓴 이유

조회와 추천처럼 서로 독립적인 읽기 전용 작업은 순차 실행할 필요가 없습니다. `Send`를 쓰면 계획 결과에 따라 동적으로 여러 Sub-Agent를 fan-out할 수 있습니다.

코드 근거:

```python
for step in steps:
    sends.append(Send(step["agent"], {
        "user_id": state["user_id"],
        "session_id": state.get("session_id", ""),
        "current_message": state.get("current_message", ""),
        "intent": plan.get("primary_intent", ""),
        "sub_intent": step["sub_intent"],
    }))
return sends
```

정량적으로는 현재 4개 Sub-Agent 중 `inquiry`, `recommend`, `security`는 read-only 또는 분석 중심으로 단독 호출이 가능하고, `transfer`만 side effect가 큰 workflow입니다. 그래서 병렬화 대상과 순차 대상이 구조적으로 분리됩니다.

이런 구조는 새 읽기 전용 agent가 추가될수록 더 유리합니다. 예를 들어 `product_recommend`, `spending_analysis`, `budget_alert` 같은 agent는 `Send` 대상으로 추가하기 쉽습니다.

## 7. State reducer를 명시한 이유

병렬 `Send`가 생기면 여러 branch가 같은 state key에 결과를 쓰게 됩니다. 기본 last-write 방식만 사용하면 결과가 덮일 수 있습니다.

그래서 `src/agents/state.py`는 reducer를 명시합니다.

```python
agent_results: Annotated[List[Dict[str, Any]], _accumulate]
agent_activity: Annotated[List[Dict[str, Any]], _accumulate]
node_logs: Annotated[List[Dict[str, Any]], _accumulate]
graph_trace: Annotated[List[str], _accumulate]
```

반대로 `intent`, `amount`, `response_type`처럼 현재 값 하나가 중요한 필드는 `_replace`를 씁니다.

이 구조는 LangGraph StateGraph의 reducer 개념과 일치합니다. StateGraph는 node들이 shared state를 읽고 partial state를 반환하며, state key에는 reducer를 둘 수 있습니다.  
출처: https://docs.langchain.com/oss/python/langgraph/graph-api

## 8. Checkpointer와 session 기반 thread_id를 쓴 이유

확인/OTP/되묻기 흐름은 한 번의 HTTP request로 끝나지 않습니다. 따라서 그래프의 중간 상태가 저장되어야 합니다.

코드 근거:

```python
_graph = build_banking_graph(checkpointer=SqliteSaver(_conn))
config = {"configurable": {"thread_id": f"{user_id}:{session_id}"}}
```

LangGraph 공식 interrupt 문서는 interrupt를 사용하려면 state를 저장할 checkpointer와 resume할 thread_id가 필요하다고 설명합니다.  
출처: https://docs.langchain.com/oss/python/langgraph/interrupts

이 프로젝트에서는 이를 통해 다음 시나리오를 처리합니다.

- 이체 확인 카드 표시 후 `확인` 입력
- OTP 입력
- 수신자 모호성 해소
- 금액 누락 시 되묻기
- 확인 대기 중 새 요청을 Supervisor로 handoff

테스트 근거도 있습니다. `tests/test_agent.py`에는 confirmation flow, cancel flow, ambiguity clarification, missing amount, new request during confirmation handoff, OTP flow 테스트가 있습니다.

## 9. A2A 디렉토리를 별도로 둔 이유

`src/agents/a2a/cards.py`는 agent의 능력 명세를 한곳에 모읍니다. 이 정보는 두 방향으로 쓰입니다.

1. 내부: Supervisor planner prompt에 "사용 가능한 agent 목록"으로 주입됩니다.
2. 외부: `/.well-known/agent-card.json`, `/api/a2a/agents`로 discovery됩니다.

코드 근거:

- `src/agents/a2a/cards.py`: `AGENT_CARDS`, `render_cards_for_prompt()`, `public_card()`
- `src/web/routes/a2a.py`: A2A discovery와 JSON-RPC invoke route
- `src/agents/supervisor/planner.py`: `render_cards_for_prompt()`를 planner prompt에 전달

별도 디렉토리로 분리한 이유는 agent 구현과 agent capability metadata의 변경 주기가 다르기 때문입니다. 구현은 `subagents/`에 있고, 외부 노출 계약은 `a2a/`에 있습니다.

## 10. Service 계층을 둔 이유

agent node 안에서 직접 모든 DB 변경을 처리하면 테스트와 감사가 어려워집니다. 그래서 실제 업무 규칙은 `src/agents/common/services/`로 분리했습니다.

예:

- `transfer_service.py`: 이체 summary 생성, 검증, 실행
- `security_rules.py`: 보안 risk rule
- `recommendation_service.py`: 추천 점수 계산
- `recipient_service.py`: 수신자 검색
- `balance_service.py`: 잔액 조회
- `alias_service.py`: 별칭 학습

이 구조의 장점은 agent graph 없이도 도메인 로직을 테스트할 수 있다는 점입니다. 실제로 `tests/test_transfer_service.py`는 수수료, 잔액 부족, 한도 초과, 0원 이체 같은 순수 업무 규칙을 검증합니다.

## 11. 확장성 관점의 근거

신규 상품추천 Agent를 추가한다고 가정하면 변경 지점은 예측 가능합니다.

| 변경 대상 | 이유 |
|---|---|
| `src/agents/subagents/product_recommend.py` | 신규 agent workflow |
| `src/agents/supervisor/graph.py` | parent graph node 등록 |
| `src/agents/common/schemas.py` | `AgentName` 허용 목록 확장 |
| `src/agents/supervisor/planner.py` | intent → agent mapping 추가 |
| `src/agents/a2a/cards.py` | discovery와 planner prompt용 capability 추가 |
| `src/web/routes/a2a.py` | 외부 단독 invoke 허용 시 builder 등록 |
| `tests/test_agent.py` | planning/fan-out regression test 추가 |

즉 확장 비용은 "아무 곳이나 수정"이 아니라 명확한 6~7개 지점으로 제한됩니다. 현재는 정적 registry 방식이라 자동 plugin 구조는 아니지만, 발표나 리뷰에서는 "확장 가능한 구조이나 registry 자동화는 보완 포인트"라고 설명하는 것이 정확합니다.

## 12. 왜 완전한 자유형 Agent loop가 아니라 명시적 Workflow인가

금융 도메인에서는 다음 이유로 명시적 workflow가 더 적합합니다.

1. 이체 실행 전 확인과 OTP가 반드시 필요합니다.
2. 보안 rule은 재현 가능해야 합니다.
3. DB 변경은 idempotency와 감사 로그를 고려해야 합니다.
4. 테스트에서 같은 입력은 같은 계획과 결과를 만들어야 합니다.
5. 실패 지점을 node 단위로 추적할 수 있어야 합니다.

LangGraph 공식 Graph API도 checkpointer 사용 시 node 재실행과 idempotency를 주의해야 한다고 설명합니다. 이 프로젝트가 `execute_node` 앞에 확인/OTP를 두고, 실제 DB 변경을 끝부분에 몰아둔 것도 이 근거와 연결됩니다.  
출처: https://docs.langchain.com/oss/python/langgraph/graph-api

## 13. 결론

이 프로젝트의 구조는 다음 네 가지 근거로 설명할 수 있습니다.

1. **프레임워크 정합성**: LangGraph 공식 구조의 state, graph, node, utility 분리 방식을 금융 agent 규모로 확장했습니다.
2. **도메인 안전성**: 이체는 workflow와 interrupt로 통제하고, 실제 실행은 결정론적 service 코드에 맡겼습니다.
3. **확장성**: Sub-Agent를 독립 subgraph로 두어 신규 agent 추가 경로가 명확합니다.
4. **검증 가능성**: planning, multi-turn, OTP, 보안 협업, service rule을 테스트로 분리해 검증할 수 있습니다.

따라서 현재 구조는 "최신 LangGraph 기능을 보여주기 위한 구조"인 동시에, 금융 이체라는 고위험 도메인에서 LLM의 자유도를 제한하고 감사 가능한 실행 흐름을 만들기 위한 구조입니다.
