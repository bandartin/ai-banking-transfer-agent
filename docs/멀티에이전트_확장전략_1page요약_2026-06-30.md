## 1. 결론
- 3개년 장기 과제이므로 **처음부터 전(全) 에이전트 분리 금지** — 경계 확정·점검·디버깅 부담만 커짐.
- **1년차 단일 파드 → 2~3년차 단계적 분리**가 가장 안전함. 분리에 앞서 **계약(Contract) 표준화**가 먼저임.

## 2. 단계별 목표 구조
- **1년차 — 단일 슈퍼에이전트 파드**
  - 화면 백엔드는 슈퍼에이전트만 호출함.
  - 슈퍼에이전트가 **로그·트레이싱·컨텍스트·로드밸런싱**을 일괄 책임짐.
  - 모든 담당자가 **표준 서비스 규약** 위에서 개발 → 표준화 효과 + 단순한 디버깅.
- **2~3년차 — 게이트웨이 + 서브에이전트 분리 배포**
  - 슈퍼에이전트는 별도 배포되어 **플래닝·오케스트레이션·통합관리**만 수행함(도메인 로직 0 유지).
  - 서브에이전트는 **A2A·MCP·HTTP**로 호출함. 외부 인터페이스(단일 진입점)는 불변임.
  - 분리 순서: **계산기·메뉴·상품(저위험) 먼저, 이체(고위험) 마지막**.

## 3. 횡단 관심사 관리 주체
- 감사로그·트레이싱·컨텍스트·성능은 **슈퍼바이저 통합 관리가 맞음**.
- 서브에이전트는 **표준 필드(agent_id·version·latency·status·error_type) 방출만**, 수집·통합·보존은 슈퍼바이저가 함 → 분리 후 trace 단절 방지.

## 4. 핵심 리스크
- **슈퍼에이전트 전담자 부재** — WBS상 '검색 에이전트'에 통합되어 책임 불명확함. 가장 무거운 컴포넌트인데 주인이 없음.
- **AWX 운영 범위 미확인** — 형상관리·재배포·로드밸런싱 제공 여부 불명. 특히 "재배포마다 AWX 전체 다운"이면 분리 배포 자체가 불가함.
