# 멀티에이전트 확장 구조 검토보고서

작성일: 2026-06-30  
대상 프로젝트: `ai-banking-transfer-agent`  
작성 목적: 현재 이체 중심 에이전트 구현을 향후 금융계산기, 메뉴탐색, 상품안내 등 다수 개발자가 참여하는 멀티에이전트 구조로 확장할 때의 설계 판단 정리

---

## 1. 검토 결론

현재 프로젝트는 이미 `Global Supervisor + Sub-Agent` 구조를 LangGraph 기반 단일 서버 안에서 구현하고 있다. `src/agents/supervisor/graph.py`의 Supervisor가 사용자 발화를 계획하고, `transfer`, `inquiry`, `recommend`, `security`, `menu_search`, `product_guide`, `financial_calculator`, `tool_agent` 등의 하위 에이전트 subgraph를 호출하는 형태다. 특히 이체 에이전트는 단순 기능 함수가 아니라 슬롯 추출, 수신자 해석, 되묻기, 확인, OTP, 실행, 보안 평가 협업까지 포함하는 도메인 워크플로를 갖고 있어 사실상 `Transfer Domain Agent`의 기준 구현으로 볼 수 있다.

따라서 본 프로젝트에 대한 판단은 다음과 같다.

1. 단기적으로는 현 구조, 즉 단일 서버 안의 Supervisor와 Sub-Agent subgraph 구조를 유지하는 것이 현실적이다.
2. 다만 여러 개발자가 각자 에이전트를 붙이는 단계로 넘어가기 전에 `Agent Contract`, `Agent Card`, 공통 응답 스키마, 테스트 책임 범위를 먼저 고정해야 한다.
3. 운영 또는 타 팀 독립 배포가 필요해지는 시점에는 각 Sub-Agent를 독립 Agent API로 분리하고, 현재 Supervisor는 `Agent Gateway`로 전환하는 것이 맞다.
4. MCP는 현재 핵심 런타임 구조로 채택하기보다, AWX/외부 AI 클라이언트 연동이 필요한 에이전트에 한해 선택적으로 붙이는 Adapter 계층으로 두는 것이 적합하다.

즉, 최종 권고안은 `단일 서버 MVP 유지 -> Agent Contract 표준화 -> Sub-Agent 독립 API 분리 -> 필요 시 MCP Adapter 추가` 순서다. 지금 바로 모든 에이전트를 마이크로서비스로 분해하면 개발 속도와 디버깅 효율이 떨어질 가능성이 높다. 반대로 현재 방식 그대로 팀 규모만 늘리면 공통 상태, 의존성, 테스트, 배포 책임이 빠르게 엉킬 수 있다. 따라서 지금 필요한 것은 구현 분리가 아니라 먼저 “계약의 분리”다.

## 2. 현재 프로젝트 구조 관찰

현재 프로젝트는 Flask 애플리케이션 위에 LangGraph 기반 에이전트 런타임을 얹은 구조다. 주요 구성은 다음과 같다.

| 영역 | 현재 구현 | 판단 |
|---|---|---|
| Global Supervisor | `src/agents/supervisor/graph.py`, `planner.py` | 사용자 의도 분류, 실행 계획 생성, Sub-Agent fan-out, 결과 취합 담당 |
| Agent Card / Discovery | `src/agents/a2a/cards.py`, `src/web/routes/a2a.py` | A2A 형식의 에이전트 메타데이터 및 JSON-RPC invoke 초안 보유 |
| 이체 에이전트 | `src/agents/subagents/transfer.py` | 가장 성숙한 Domain Agent. HITL, OTP, 보안 협업, 실행 멱등성 포함 |
| 보안 에이전트 | `src/agents/subagents/security.py` | 이체 전 리스크 평가 협업에 활용 |
| 조회/추천 에이전트 | `inquiry.py`, `recommend.py` | 읽기 계열 Sub-Agent로 Supervisor 병렬 호출 검증에 적합 |
| 메뉴/상품/계산 에이전트 | `menu_search.py`, `product_guide.py`, `financial_calculator.py` | 향후 타 개발자 확장 예시와 맞닿아 있음 |
| Tool Calling | `src/agents/tool_calling/registry.py` | read/prepare 중심의 도구 경계와 side-effect 정책을 일부 갖춤 |
| AWX/MCP 연동 | `src/agents/tool_calling/awx_mcp.py`, `docs/tool_calling_phase9_awx_mcp_adapter.md` | disabled-by-default, allowlist 기반 Adapter 방향이 이미 정리됨 |
| 테스트 | `tests/test_agent.py`, `tests/test_tool_calling_phase*.py`, `tests/test_integration_readiness.py` | 통합 흐름, HITL, readiness, 정책 테스트가 존재 |

현재 구조의 강점은 “멀티에이전트 개념 검증”이 이미 상당 부분 끝나 있다는 점이다. Supervisor는 `ExecutionPlan`을 만들고, LangGraph `Send`를 통해 여러 Sub-Agent를 병렬 호출할 수 있다. 이체 진행 중 사용자가 잔액 조회처럼 새로운 요청을 하면 `Command(graph=Command.PARENT)`로 부모 Supervisor에게 제어를 돌려주는 흐름도 구현되어 있다. 이는 단순 라우터가 아니라 계층형 멀티에이전트 구조의 핵심 패턴을 이미 시연한 것이다.

다만 현재 구조는 아직 “여러 개발자가 독립적으로 붙는 운영 구조”라기보다 “하나의 코드베이스 안에서 여러 에이전트 패턴을 검증한 MVP 구조”에 가깝다. 새 개발자가 금융계산기나 메뉴탐색 에이전트를 추가하려면 지금은 `AgentName` Literal, Agent Card, Supervisor route, subgraph builder, 테스트, UI 응답 타입 등을 여러 곳에서 동시에 수정해야 한다. 이 방식은 소수 개발자에게는 빠르지만, 담당자가 늘어나면 변경 충돌과 계약 불일치가 발생하기 쉽다.

## 3. 제공 문서와 현재 프로젝트의 적합도 판단

사용자가 작성한 문서의 핵심 결론인 `슈퍼바이저 에이전트 서버 + 서브 에이전트별 독립 Agent API + 필요 시 MCP Adapter` 구조는 장기 방향으로 타당하다. 특히 “서브 에이전트 구현 개발자가 별도로 존재하고, 유지보수와 테스트도 각자 수행한다”는 전제에서는 독립 Agent API가 가장 명확한 책임 경계를 제공한다.

그러나 현재 프로젝트에 바로 적용할 때는 단계 조정이 필요하다. 현재 프로젝트는 이미 단일 서버 MVP 단계와 일부 확장형 실험을 동시에 갖고 있다. 이체 에이전트는 성숙도가 높고 상태 전이가 복잡하다. 반면 금융계산기, 메뉴탐색, 상품안내 등은 독립 개발자가 붙기 쉬운 읽기/계산/RAG 계열에 가깝다. 따라서 모든 에이전트를 동일한 방식으로 한 번에 독립 API화하기보다는, 위험도와 상태 복잡도에 따라 분리 우선순위를 달리해야 한다.

우선순위는 다음처럼 잡는 것이 적절하다.

| 우선순위 | 대상 | 이유 |
|---|---|---|
| 1 | Agent Contract / Agent Card 표준화 | 모든 개발자가 따를 공통 계약이 먼저 필요 |
| 2 | 읽기/계산 계열 에이전트 표준 템플릿화 | 금융계산기, 메뉴탐색, 상품안내는 side effect가 낮아 확장 실험에 적합 |
| 3 | Supervisor Registry 기반화 | 새 에이전트 추가 시 Supervisor 코드 수정 범위를 줄여야 함 |
| 4 | 독립 Agent API 분리 | 담당 팀과 배포 주기가 갈릴 때 적용 |
| 5 | MCP Adapter 추가 | 외부 AI 클라이언트 또는 AWX MCP 연동 수요가 확정될 때 적용 |

현재 이체 에이전트는 즉시 독립 API로 분리하기보다 기준 구현으로 삼는 편이 낫다. 이체는 금전 이동이라는 side effect가 있고, HITL, OTP, idempotency, security consult, checkpoint resume이 얽혀 있다. 섣불리 서비스 경계를 나누면 트랜잭션, 세션 상태, 승인 흐름이 오히려 복잡해질 수 있다. 대신 이체 에이전트가 어떤 입력을 받고 어떤 결과를 반환해야 하는지 `Transfer Agent Contract`를 먼저 문서화하고, 이후 독립 API 후보로 전환하는 것이 안전하다.

## 4. 권장 목표 아키텍처

본 프로젝트의 목표 구조는 다음과 같이 잡는 것이 좋다.

```text
Client / UI
  ↓
Global Supervisor / Agent Gateway
  ↓
Agent Registry
  ↓
Sub-Agent Contract Layer
  ├── Transfer Agent
  ├── Inquiry Agent
  ├── Recommend Agent
  ├── Security Agent
  ├── Menu Search Agent
  ├── Product Guide Agent
  └── Financial Calculator Agent
       ↓
Optional Agent API / MCP Adapter / AWX Tool Adapter
```

초기에는 이 구조가 물리적으로 하나의 서버 안에 있어도 된다. 중요한 것은 코드 안에서 다음 경계를 명확히 분리하는 것이다.

1. Supervisor는 각 도메인 내부의 세부 툴을 직접 알지 않는다.
2. Sub-Agent는 자기 도메인의 데이터, 정책, 테스트를 책임진다.
3. Supervisor와 Sub-Agent 사이에는 공통 `invoke` 입력과 공통 응답 envelope이 존재한다.
4. Agent Card는 prompt용 설명이 아니라 운영 계약의 일부로 관리한다.
5. side effect가 있는 기능은 `read`, `prepare`, `confirm`, `execute` 같은 실행 권한 단계를 명확히 갖는다.

현재 `tool_calling/registry.py`는 이 방향과 잘 맞는다. read-only 도구와 transfer-prep 도구를 분리하고, 실행은 기존 TransferAgent 워크플로에 남겨둔 판단은 금융 도메인에서 특히 타당하다. 향후 타 개발자가 에이전트를 추가할 때도 “읽기/계산은 도구화 가능, 실행은 승인 경계 필요”라는 원칙을 공통 규칙으로 삼아야 한다.

## 5. 팀 개발을 위한 Agent Contract 제안

타 개발자가 각자 에이전트를 추가하려면 최소한 다음 산출물을 에이전트별로 요구해야 한다.

| 산출물 | 설명 | 예시 위치 |
|---|---|---|
| Agent Card | 에이전트명, 책임 범위, 지원 skill, 금지 범위, side effect 정책 | `src/agents/a2a/cards.py` 또는 별도 manifest |
| Invoke Contract | 입력/출력 Pydantic schema | `src/agents/common/schemas.py` |
| Subgraph Builder | `build_xxx_subgraph()` 표준 함수 | `src/agents/subagents/<agent>.py` |
| Routing Hint | intent, examples, primary/optional agent 설정 | Agent Card 또는 registry |
| Unit Test | 도메인 내부 함수 검증 | `tests/test_<agent>.py` |
| Contract Test | Supervisor가 호출 가능한지 검증 | `tests/test_agent_contracts.py` |
| Scenario Eval | 실제 사용자 질의와 기대 agent 선택 | `tests` 또는 `docs/evals` |
| Observability Field | agent, event, latency, status, error_type | `agent_activity`, tracing |

특히 공통 응답 envelope은 지금보다 더 명시적으로 고정하는 것이 좋다. 현재 `agent_results`는 `agent`, `kind`, `text`, `data` 중심으로 동작한다. MVP에는 충분하지만 독립 개발자가 늘어날 경우 다음 필드가 필요하다.

```json
{
  "status": "completed",
  "agent_id": "financial_calculator",
  "agent_version": "1.0.0",
  "kind": "calculation",
  "answer_markdown": "...",
  "data": {},
  "evidence": [],
  "confidence": 1.0,
  "limitations": [],
  "requires_user_confirmation": false,
  "side_effect_level": "read",
  "error": null
}
```

이 스키마는 모든 에이전트에 똑같이 많은 정보를 요구하자는 뜻이 아니다. 금융계산기는 `confidence=1.0`, `evidence=[]`, `limitations=[계산 가정]`처럼 채울 수 있고, 메뉴탐색이나 상품안내는 검색 근거 문서 metadata를 evidence로 채울 수 있다. 이체 에이전트는 `requires_user_confirmation`, `side_effect_level`, `pending_state`를 명확히 반환해야 한다.

또한 Agent Card는 현재처럼 Supervisor prompt에 넣는 설명 문자열로만 관리하면 한계가 있다. 앞으로는 다음 필드를 추가하는 것을 권장한다.

```yaml
agent_id: transfer
owner: transfer-agent-owner
version: 2.0.0
responsibilities:
  - transfer_preparation
  - transfer_confirmation
  - transfer_execution_with_approval
not_responsible_for:
  - product_policy_answer
  - menu_navigation
side_effect_level: execute_with_approval
default_timeout_ms: 30000
input_schema: TransferInvokeRequest
output_schema: AgentInvokeResponse
contract_tests:
  - tests/test_agent_contracts.py::test_transfer_contract
```

## 6. Supervisor 설계 방향

현재 Supervisor는 얕은 라우터와 결과 취합자의 역할을 이미 수행한다. 향후에는 여기에 두 가지 기능을 보강해야 한다.

첫째, 에이전트 목록을 코드 상수에서 점진적으로 registry 기반으로 옮겨야 한다. 현재는 `AgentName` Literal, `AGENT_CARDS`, `build_banking_graph()`, A2A route builder 등 여러 지점에 에이전트 목록이 분산되어 있다. 개발자가 `menu_search` 같은 신규 에이전트를 추가할 때 한 곳을 빠뜨리면 LLM planner, rule planner, A2A endpoint, test 중 일부만 동작할 수 있다. 따라서 중기적으로는 `Agent Registry`를 단일 진실 공급원으로 만들고, Supervisor prompt, route validation, A2A card, contract test가 이 registry에서 파생되도록 하는 것이 좋다.

둘째, Supervisor가 도메인 판단을 가져가지 않도록 해야 한다. 예를 들어 금융계산기의 계산식 검증, 메뉴탐색의 검색 컬렉션 선택, 상품안내의 근거 문서 선택은 각 Domain Agent 내부 책임이다. Supervisor는 “어떤 에이전트를 부를지”, “여러 결과를 어떻게 합칠지”, “사용자에게 한계를 어떻게 설명할지”에 집중해야 한다.

현재 이체 에이전트 안에 SecurityAgent를 직접 호출하는 구조는 금융 실행 업무에서는 타당하다. 이체는 보안 검토가 도메인 워크플로의 일부이므로 TransferAgent 내부 Domain Supervisor가 SecurityAgent를 협업 대상으로 쓰는 것은 자연스럽다. 다만 장기적으로는 Global Supervisor가 호출하는 `security_report`와 TransferAgent 내부의 `security_assess_transfer`를 명칭과 contract로 구분해야 한다. 같은 SecurityAgent라도 “사용자 질의에 대한 보안 리포트”와 “이체 실행 전 리스크 판정”은 SLA와 응답 스키마가 다르기 때문이다.

## 7. 독립 API 및 MCP Adapter 전환 판단

독립 Agent API는 다음 조건 중 두 가지 이상이 충족될 때 전환하는 것이 적절하다.

1. 해당 에이전트 담당 개발자 또는 팀이 별도로 존재한다.
2. 해당 에이전트만 독립 배포하거나 롤백해야 한다.
3. 의존성이 다른 에이전트와 충돌한다.
4. 응답 시간이 길거나 리소스 사용량이 커서 별도 스케일링이 필요하다.
5. 외부 시스템 권한 또는 감사 로그를 별도로 관리해야 한다.

금융계산기와 메뉴탐색은 독립 API 전환 후보로 적합하다. 금융계산기는 결정론 계산과 상품별 룰 확장이 핵심이므로 독립 테스트가 쉽다. 메뉴탐색은 AWX 지식 저장소나 RAG 검색 품질이 핵심이므로 검색 adapter, 문서 metadata, evidence 품질을 담당 개발자가 독립적으로 관리하기 좋다.

이체 에이전트는 반대로 마지막에 분리하는 편이 낫다. 이체는 사용자 세션, 확인 대기, OTP, 실행 멱등성, DB 트랜잭션, 보안 정책이 촘촘히 연결되어 있다. 이체를 독립 API화하려면 먼저 다음이 준비되어야 한다.

1. 세션 resume과 pending state를 API 경계 밖에서도 보존할 수 있어야 한다.
2. 이체 실행 요청에 idempotency key가 강제되어야 한다.
3. 승인 전/승인 후 상태가 명확히 분리되어야 한다.
4. 실패 시 사용자에게 노출할 메시지와 내부 에러가 구분되어야 한다.
5. 감사 로그가 Supervisor와 TransferAgent 양쪽 trace_id로 연결되어야 한다.

MCP Adapter는 현재 문서의 결론처럼 “선택 계층”으로 두는 것이 맞다. 이미 `docs/tool_calling_phase9_awx_mcp_adapter.md`에서 disabled-by-default, allowlist, side effect 제한, 관측성 span을 강조하고 있다. 이 방향은 유지해야 한다. MCP tool description이 실행 권한을 결정하게 두면 안 되며, 애플리케이션 소유의 allowlist와 policy gate가 최종 권한을 결정해야 한다.

## 8. 단계별 실행 제안

### Phase 1. 계약 표준화

목표는 신규 개발자가 “어디를 어떻게 추가해야 하는지”를 한눈에 알 수 있게 만드는 것이다.

- `AgentInvokeResponse` 공통 Pydantic schema 추가
- Agent Card 필수 필드 확정
- 신규 Sub-Agent 추가 체크리스트 작성
- `AgentName` Literal, Agent Card, graph node 등록의 중복 관리 축소
- 이체 에이전트의 contract를 기준 샘플로 문서화

### Phase 2. 읽기/계산 에이전트 템플릿화

금융계산기, 메뉴탐색, 상품안내는 타 개발자가 확장하기 좋은 영역이다. 이들을 “표준 Sub-Agent 템플릿”으로 다듬는다.

- `build_<agent>_subgraph()` 표준 시그니처 유지
- `agent_results` 공통 envelope 적용
- evidence/limitations 필드 추가
- 도메인별 unit test와 Supervisor routing test 분리
- side effect는 기본 `read` 또는 `compute`로 제한

### Phase 3. Registry 기반 Supervisor 전환

현재 Supervisor 코드에 하드코딩된 에이전트 목록을 registry 중심으로 정리한다.

- registry에서 Agent Card, planner prompt, A2A public card 생성
- 신규 에이전트 추가 시 수정 지점을 최소화
- routing rule과 LLM planner validation을 registry 기반으로 수행
- contract test에서 모든 registered agent의 builder와 schema 검증

### Phase 4. 독립 Agent API 파일럿

가장 먼저 독립 API화할 후보는 금융계산기 또는 메뉴탐색이다. 두 영역 모두 side effect가 낮고, 상태 유지가 상대적으로 단순하다.

- `/v1/agents/{agent_id}/metadata`
- `/v1/agents/{agent_id}/invoke`
- `/v1/agents/{agent_id}/health`
- OpenAPI spec
- Supervisor HTTP client adapter
- contract test와 timeout test

### Phase 5. MCP Adapter 선택 적용

외부 AI 도구나 AWX MCP 연동이 확정된 에이전트에만 Adapter를 붙인다.

- API response를 MCP tool result로 변환
- tool allowlist와 side effect 정책 적용
- trace_id, tool_name, side_effect_level 기록
- 민감 payload redaction 유지

## 9. 주요 리스크와 대응

| 리스크 | 설명 | 대응 |
|---|---|---|
| 에이전트 추가 지점 분산 | 새 agent 추가 시 graph, card, schema, planner를 모두 수정해야 함 | Agent Registry를 단일 진실 공급원으로 전환 |
| 응답 스키마 불일치 | 개발자별 `data` 구조가 달라 Supervisor 병합이 복잡해짐 | 공통 envelope + 도메인별 `data` schema 분리 |
| Supervisor 비대화 | Supervisor가 도메인 내부 판단까지 흡수할 위험 | Supervisor 책임을 routing, orchestration, synthesis로 제한 |
| 이체 실행 경계 약화 | tool calling 또는 MCP를 통해 실행성 작업이 우회될 위험 | side effect policy, approval gate, allowlist, idempotency 강제 |
| 관측성 단절 | 독립 API 분리 후 trace가 끊길 수 있음 | trace_id, agent_version, prompt_version, status 표준화 |
| 테스트 책임 모호 | 통합 테스트만 늘고 도메인 품질 책임이 흐려짐 | unit/contract/routing/e2e eval 계층 분리 |

## 10. 최종 권고

현재 프로젝트는 멀티에이전트 아키텍처를 새로 도입해야 하는 상태가 아니라, 이미 구현된 멀티에이전트 MVP를 팀 개발 가능 구조로 정리해야 하는 상태다. 이체 에이전트는 Domain Agent 기준 구현으로 삼을 만하며, Supervisor의 planning, 병렬 fan-out, HITL resume, SecurityAgent 협업, A2A card, AWX MCP adapter 실험도 확장 방향과 잘 맞는다.

다만 팀 확장을 앞두고 가장 먼저 해야 할 일은 물리적 서비스 분리가 아니다. 우선 `Agent Contract`와 `Agent Registry`를 표준화해야 한다. 그 다음 금융계산기, 메뉴탐색, 상품안내처럼 side effect가 낮은 에이전트를 템플릿화하여 타 개발자가 붙을 수 있는 개발 규약을 만든다. 이후 실제 담당 팀, 배포 주기, 운영 책임이 갈라지는 에이전트부터 독립 Agent API로 분리한다. MCP는 외부 연동이 필요한 경우에만 Adapter로 붙이고, 실행 권한은 반드시 애플리케이션 policy가 통제해야 한다.

보고 관점에서 한 문장으로 정리하면 다음과 같다.

> 본 프로젝트는 현재 단일 서버 기반의 계층형 멀티에이전트 MVP로는 적절하게 구현되어 있으며, 향후 다수 개발자 참여 구조로 확장하기 위해서는 즉시 마이크로서비스화하기보다 Agent Contract, Registry, 테스트 책임, side-effect 정책을 먼저 표준화한 뒤 Sub-Agent별 독립 API와 MCP Adapter를 단계적으로 적용하는 것이 가장 안전하다.
