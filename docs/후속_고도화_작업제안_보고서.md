# 후속 고도화 작업 제안 보고서

## 1. 개요

현재까지 멀티턴 follow-up memory와 Slot 추출 고도화를 통해 “직전 대화 맥락을 참조하는 이체”와 “LLM/Rule 기반 안전한 Slot 추출”의 기반을 마련했다. 다음 단계는 이 기반을 실제 뱅킹 UX와 운영 안정성 관점으로 확장하는 것이 적절하다.

## 2. 우선 추진 과제

### 2.1 Slot 추출 평가셋 구축

- 한국어 이체 발화 100~200개를 golden dataset으로 작성한다.
- 금액, 수신자, 은행, 출금계좌, 메모, 반복이체, 후속 참조 표현을 포함한다.
- Rule parser와 LLM structured output을 동일 기준으로 평가한다.
- 기대 효과: Slot 품질을 감각이 아니라 수치로 관리할 수 있다.

### 2.2 확인 단계 수정 루프 고도화

- 현재는 확인 단계에서 금액 수정 중심으로 처리한다.
- 후속 작업에서는 수신자 변경, 메모 변경, 출금계좌 변경까지 지원한다.
- 예: “아니 지연한테”, “메모는 밥값으로”, “비상금통장에서 보내”
- 기대 효과: 사용자가 처음부터 다시 말하지 않아도 이체 정보를 자연스럽게 수정할 수 있다.

### 2.3 검증 실패 복구 멀티턴

- 잔액 부족, 한도 초과, 출금계좌 불일치 시 단순 종료가 아니라 복구 선택지를 제공한다.
- 예: “잔액이 부족합니다. 금액을 줄이거나 다른 계좌를 선택하시겠어요?”
- 기대 효과: 실패 경험을 대화형 문제 해결 흐름으로 전환한다.

### 2.4 출금계좌 선택 UX 강화

- 현재는 출금계좌 힌트가 있으면 계좌를 찾고, 없으면 주계좌를 사용한다.
- 후속 작업에서는 복수 계좌가 있는 사용자의 경우 필요 시 계좌 선택 카드를 제공한다.
- 예: “어느 계좌에서 보낼까요? 1. 주계좌 2. 비상금통장”
- 기대 효과: 실제 뱅킹 앱에 가까운 UX와 안전성을 확보한다.

### 2.5 LLM Slot 추출 운영 안전장치

- `confidence`가 낮거나 `ambiguous_fields`가 있으면 바로 실행하지 않고 확인 질문을 생성한다.
- LLM이 Rule parser로 검증되지 않은 금액을 제시하면 반드시 재확인한다.
- 추출 결과와 근거를 `AgentRunLog`에 별도 저장해 운영 모니터링 가능성을 높인다.
- 기대 효과: LLM 사용 시에도 금융 안전 경계를 유지한다.

## 3. 중기 확장 과제

### 3.1 수신자 등록 및 계좌번호 입력 플로우

- 즐겨찾기에 없는 사람에게 보낼 때 이름, 은행, 계좌번호를 단계적으로 입력받는다.
- 계좌번호 형식 검증과 최종 확인 interrupt를 적용한다.

### 3.2 자동이체 등록·수정·해지 Agent

- 현재 자동이체는 조회와 일부 recurring hint 기반 이체에 머무른다.
- 등록, 금액 변경, 날짜 변경, 해지까지 별도 관리 플로우로 확장한다.

### 3.3 보안 설명형 멀티턴

- 보안 위험도가 높을 때 “왜 위험한가요?”에 답할 수 있도록 리스크 규칙 설명을 대화형으로 제공한다.
- 고위험 거래는 추가 확인 문구 또는 강화 인증 흐름을 적용한다.

## 4. 권장 진행 순서

1. Slot 추출 평가셋 구축
2. 확인 단계 수정 루프 고도화
3. 검증 실패 복구 멀티턴
4. 출금계좌 선택 카드 UX
5. LLM Slot 운영 모니터링 및 로그 확장
6. 수신자 등록/자동이체/보안 설명형 멀티턴 확장

## 5. 결론

다음 개발의 핵심은 “더 많은 기능”보다 “불확실한 입력을 안전하게 다루는 대화 흐름”이다. Slot 추출 품질을 평가셋으로 관리하고, 확인·수정·복구 루프를 강화하면 현재 Agent는 데모 수준을 넘어 실제 뱅킹 업무 흐름에 가까워질 수 있다.
