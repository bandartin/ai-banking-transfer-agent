# AI Banking Transfer Agent 예상 질문 답변

이 문서는 `ai-banking-transfer-agent` 프로젝트 발표, 코드 리뷰, 기술 면접, 시연 질의응답에 대비하기 위한 예상 질문 20개와 답변입니다.

프로젝트의 핵심은 LangGraph 기반 Supervisor/Leader Agent가 사용자 요청을 실행 계획으로 바꾸고, `transfer`, `inquiry`, `recommend`, `security` 하위 에이전트에 작업을 위임하는 구조입니다. 이체처럼 위험도가 높은 업무는 확인, OTP, 보안 평가를 거쳐 결정론적 코드로 실행하고, LLM은 주로 의도 분류, 계획 수립, 표현 보정에 제한적으로 사용합니다.

## 1. 새로운 에이전트들을 신규로 결합하여, 예를 들어 상품추천 Agent를 리더 에이전트 하위에 더 많이 확장할 수 있나요?

네, 현재 구조에서는 확장할 수 있습니다. Supervisor 그래프가 하위 에이전트를 LangGraph subgraph 노드로 등록하고, Planner가 `ExecutionPlan.steps`에 어떤 에이전트를 호출할지 기록한 뒤 `Send`로 fan-out 하는 방식이기 때문입니다.

예를 들어 상품추천 Agent를 추가하려면 다음 변경이 필요합니다.

1. `src/agents/subagents/product_recommend.py` 같은 신규 subgraph를 만든다.
2. `src/agents/supervisor/graph.py`의 `build_banking_graph()`에 노드로 등록한다.
3. `src/agents/common/schemas.py`의 `AgentName` 허용 목록에 신규 agent key를 추가한다.
4. `src/agents/supervisor/planner.py`의 rule planner 또는 LLM planner prompt에 신규 intent 매핑을 추가한다.
5. `src/agents/a2a/cards.py`에 Agent Card를 추가해 discovery와 planner prompt에 반영한다.
6. 필요하면 `/api/a2a/agents/<agent_key>/invoke`에서 단독 호출 가능한 builder 목록에도 등록한다.

현재 구조의 장점은 리더 에이전트가 모든 업무 로직을 직접 알 필요 없이 "어떤 agent에게 어떤 sub_intent를 보낼지"만 결정하면 된다는 점입니다. 다만 지금의 `AgentName`이 `Literal["transfer", "inquiry", "recommend", "security"]`로 고정되어 있어 완전한 플러그인형 확장까지는 아닙니다.

보완 포인트: agent registry를 코드 상수 대신 설정 파일이나 DB 기반 registry로 바꾸면, 신규 에이전트를 추가할 때 schema, graph, A2A route, planner mapping을 여러 파일에서 동시에 수정해야 하는 부담을 줄일 수 있습니다.

## 2. Workflow 형태로 개발한 이유와 장단점, 한계가 무엇인가요?

Workflow 형태로 개발한 이유는 금융 이체 업무가 단순 대화형 응답이 아니라 순서, 검증, 사용자 확인, 보안 판단, 실행, 기록이 필요한 절차형 업무이기 때문입니다. 이체는 "대충 답변"하면 안 되고, 수신자 확인, 금액 검증, 잔액 검증, OTP 여부 판단, 사용자 최종 확인, DB 반영이 정해진 순서로 진행되어야 합니다.

장점은 다음과 같습니다.

1. 실행 흐름이 명확해 디버깅과 감사 추적이 쉽습니다.
2. `interrupt()`와 `Command(resume=...)`로 Human-in-the-Loop를 자연스럽게 구현할 수 있습니다.
3. 각 node가 맡는 책임이 작아 테스트하기 쉽습니다.
4. `Send`를 통해 조회와 추천처럼 독립적인 작업을 병렬 실행할 수 있습니다.
5. LLM의 자유도를 제한하고, 실제 금융 실행은 결정론적 서비스 코드로 통제할 수 있습니다.

단점과 한계도 있습니다.

1. 새로운 흐름이 추가될 때 graph node와 edge 설계가 필요해 초기 개발 비용이 있습니다.
2. 매우 자유로운 대화나 예외적인 요청은 workflow 밖으로 벗어날 수 있습니다.
3. node 간 state contract가 커지면 상태 관리가 복잡해질 수 있습니다.
4. 현재는 graph가 코드에 강하게 정의되어 있어 운영 중 동적 변경은 어렵습니다.

보완 포인트: workflow 정의와 agent registry를 선언형 설정으로 분리하고, 각 node의 입출력 schema를 더 엄격히 검증하면 확장성과 유지보수성이 좋아집니다.

## 3. Planning을 저렇게 구현한 이유가 무엇인가요?

Planning은 "사용자 문장을 바로 실행"하지 않고, 먼저 `ExecutionPlan`이라는 구조화된 계획으로 바꾸기 위해 구현했습니다. 이 계획에는 호출할 agent, sub_intent, 선택 이유, 병렬 실행 여부, primary intent가 들어갑니다.

이렇게 한 이유는 세 가지입니다.

첫째, Supervisor가 하위 에이전트 선택을 명시적으로 남길 수 있습니다. UI의 실행 계획 패널과 `AgentRunLog.plan_json`에 어떤 판단을 했는지 기록되므로 시연과 디버깅에 유리합니다.

둘째, LLM과 rule fallback을 함께 사용할 수 있습니다. OpenAI API가 설정되어 있으면 LLM 기반 structured output을 시도하고, 실패하거나 API key가 없으면 `rule_plan()`이 결정론적으로 계획을 만듭니다. 따라서 데모 환경에서도 안정적으로 동작합니다.

셋째, 이체 같은 고위험 작업은 안전 규칙을 Planning 단계에서 한 번 더 제한할 수 있습니다. 현재 `_is_sane()`은 `transfer`가 포함된 계획에 다른 agent가 섞이면 거부합니다. 이체는 확인, OTP, 보안 평가가 얽힌 절차라 단독 흐름으로 태우는 것이 안전합니다.

보완 포인트: 현재 rule planner는 intent 키워드 기반 성격이 강합니다. 실제 운영에서는 사용자 발화 평가 dataset을 만들고, planner 결과에 대한 regression test를 추가해 오분류를 줄이는 것이 좋습니다.

## 4. A2A가 여기서 동작할 때 용이한 점은 무엇인가요?

A2A의 가장 큰 장점은 에이전트의 능력을 표준적인 card와 invoke interface로 노출한다는 점입니다. 이 프로젝트에서는 `/.well-known/agent-card.json`, `/api/a2a/agents`, `/api/a2a/agents/<agent_key>`, `/api/a2a/agents/<agent_key>/invoke`를 통해 외부 시스템이 agent 목록과 능력을 발견하고 JSON-RPC 형태로 호출할 수 있습니다.

또한 내부적으로도 A2A 개념이 유용합니다. `TransferAgent`가 확인 카드 생성 전에 `SecurityAgent`를 호출해 리스크 평가를 받는 구조는 agent 간 협업의 예시입니다. 이 덕분에 이체 로직과 보안 판단 로직을 분리하면서도 하나의 workflow 안에서 결합할 수 있습니다.

용이한 점은 다음과 같습니다.

1. agent의 기능 설명이 Agent Card에 모여 있어 discovery가 쉽습니다.
2. Supervisor prompt에도 Agent Card 요약을 넣을 수 있어 LLM planner가 사용 가능한 도구 목록을 이해하기 쉽습니다.
3. read-only agent인 `inquiry`, `recommend`, `security`는 외부에서 stateless하게 호출하기 좋습니다.
4. 나중에 각 agent를 별도 서버로 분리해도 protocol surface를 유지할 수 있습니다.

한계도 있습니다. 현재 `transfer`는 확인과 OTP가 필요한 Human-in-the-Loop 업무라 직접 A2A invoke를 막고 Supervisor 경유만 허용합니다. 이는 안전한 선택이지만, 외부 A2A client가 장기 실행 task와 resume을 처리하는 완전한 프로토콜까지 구현된 것은 아닙니다.

보완 포인트: 운영 수준의 A2A로 확장하려면 task 상태 조회, 인증/인가, callback 또는 streaming, 장기 실행 resume protocol을 명확히 해야 합니다.

## 5. 런타임 컨텍스트를 사용한 이유와, 그로 인한 장단점이 무엇이었나요?

런타임 컨텍스트는 LangGraph의 `context_schema=BankingContext`로 정의되어 있고, 각 node는 `runtime.context`를 통해 사용자 정보, LLM 설정, OTP 기준, 수수료, 세션 정보를 읽습니다.

사용한 이유는 State와 Context의 성격이 다르기 때문입니다. State는 그래프가 진행되면서 바뀌고 체크포인트에 저장되어야 하는 값입니다. 예를 들어 수신자 alias, 금액, 보안 평가 결과, 응답 타입은 State입니다. 반면 Context는 이번 invoke 동안 고정된 실행 환경입니다. 예를 들어 user_id, 나이, 고객 등급, risk_profile, llm_provider, otp_threshold는 매 node에서 참고하지만 node가 수정할 값은 아닙니다.

장점은 다음과 같습니다.

1. Flask의 `current_app` 의존성을 agent 내부에서 제거해 테스트와 A2A 호출이 쉬워졌습니다.
2. 같은 graph라도 사용자별 나이, 위험 등급, LLM 설정을 다르게 주입할 수 있습니다.
3. State에 설정값이 섞이지 않아 체크포인트가 더 깔끔해집니다.
4. 결정론적 테스트에서 `BankingContext(llm_provider="deterministic")`처럼 조건을 고정하기 쉽습니다.

단점은 Context가 체크포인트에 저장되지 않는다는 점입니다. interrupt 후 resume할 때도 동일한 의미의 Context를 다시 만들어 주어야 합니다. 또한 Context에 너무 많은 값을 넣으면 사실상 전역 설정 객체처럼 커질 수 있습니다.

보완 포인트: Context 필드를 보안, 사용자 프로필, 런타임 설정 등 하위 dataclass로 나누면 규모가 커졌을 때 더 관리하기 쉽습니다.

## 6. Supervisor Agent와 Sub-Agent를 분리한 이유는 무엇인가요?

Supervisor는 "무엇을 할지"를 결정하고, Sub-Agent는 "어떻게 처리할지"를 담당하도록 책임을 나누기 위해 분리했습니다. 예를 들어 Supervisor는 사용자 요청이 잔액 조회인지, 추천인지, 이체인지 판단해 계획을 만들고, 실제 잔액 조회는 `InquiryAgent`, 추천은 `RecommendAgent`, 이체는 `TransferAgent`, 보안 평가는 `SecurityAgent`가 처리합니다.

이 구조는 단일 거대 agent보다 변경 영향 범위가 작습니다. 추천 알고리즘을 바꾸더라도 이체 확인/OTP 흐름에 영향을 주지 않고, 보안 rule을 바꾸더라도 조회 agent는 그대로 둘 수 있습니다.

보완 포인트: 현재 Sub-Agent 간 공통 interface는 `agent_results`, `agent_activity` 관례에 가깝습니다. 공통 base schema 또는 helper를 더 강화하면 신규 agent 추가 시 실수를 줄일 수 있습니다.

## 7. 이체 업무에서 LLM에게 실행 결정을 맡기지 않은 이유는 무엇인가요?

금융 이체는 금액, 수신자, 잔액, 수수료, 보안 조건이 정확해야 하므로 LLM에게 최종 실행 결정을 맡기지 않았습니다. LLM은 자연어 해석, 계획, 응답 문장 보정에는 유용하지만, 실제 계좌 잔액 차감이나 OTP 필요 여부 같은 결정은 감사 가능하고 재현 가능한 Python 코드와 DB transaction으로 처리해야 합니다.

현재 프로젝트에서 LLM은 API key가 있을 때 planner structured output이나 응답 polish에 사용될 수 있고, API key가 없으면 deterministic parser와 rule planner가 동작합니다. 이체 검증, 보안 rule, execute logic은 서비스 코드가 담당합니다.

보완 포인트: LLM slot extraction을 사용할 경우에도 추출 결과에 대한 validator, confidence threshold, 사용자 확인 단계를 유지해야 합니다.

## 8. TransferAgent에서 확인, OTP, 되묻기를 `interrupt()`로 구현한 이유는 무엇인가요?

확인, OTP, 수신자 모호성 해소, 금액 되묻기는 모두 사용자의 추가 입력이 필요한 중간 중단 지점입니다. LangGraph의 `interrupt()`를 쓰면 그래프 실행을 해당 node에서 멈추고, 다음 사용자 메시지가 들어왔을 때 `Command(resume=...)`으로 정확히 그 위치에서 이어갈 수 있습니다.

이 방식은 수동으로 세션 상태 머신을 구현하는 것보다 자연스럽습니다. 체크포인터가 thread_id별로 상태를 저장하므로, 사용자가 "확인", "취소", "3만원으로 바꿔줘", "잔액 얼마야?" 같은 입력을 했을 때 이전 context를 유지한 채 처리할 수 있습니다.

보완 포인트: interrupt 종류별 payload schema를 더 명확히 타입화하면 프론트엔드 렌더링과 백엔드 resume 처리가 더 안전해집니다.

## 9. 확인 대기 중 사용자가 다른 요청을 하면 어떻게 처리하나요?

`TransferAgent.confirm_node()`는 확인 대기 중 입력이 단순 확인/취소/금액 수정인지, 아니면 새로운 요청인지 판단합니다. 예를 들어 이체 확인 카드가 떠 있는 상태에서 사용자가 "잔액 얼마야?"라고 물으면 `Command(graph=Command.PARENT, goto="plan")`을 통해 부모 Supervisor의 planning 단계로 제어를 돌립니다.

이 설계는 대화가 실제 사용자처럼 흘러가게 해줍니다. 사용자는 확인 카드가 떠 있다고 해서 반드시 확인이나 취소만 해야 하는 것이 아니라, 중간에 조회 요청을 할 수 있습니다.

보완 포인트: 현재 새 요청 판단은 parser rule에 의존합니다. 더 다양한 자연어 표현을 처리하려면 intent classifier와 테스트 예시를 늘리는 것이 좋습니다.

## 10. 병렬 실행은 어떤 경우에 유리하고, 어떤 경우에는 피해야 하나요?

병렬 실행은 서로 독립적인 read-only 작업에 유리합니다. 예를 들어 "잔액 보여주고 자주 보내는 사람 추천해줘"는 `InquiryAgent`와 `RecommendAgent`가 서로 영향을 주지 않으므로 `Send`로 동시에 실행할 수 있습니다. 결과는 `respond_node()`에서 계획 순서에 맞게 정렬해 합칩니다.

반면 이체는 병렬 실행을 피해야 합니다. 이체는 수신자 해석, 금액 확정, 보안 평가, 사용자 확인, OTP, 실행이 순차적이고 상태 의존적입니다. 그래서 `transfer`가 포함된 계획은 단독 step으로 제한합니다.

보완 포인트: 각 agent card에 `read_only`, `requires_confirmation`, `side_effect` 같은 metadata를 추가하면 planner가 병렬 가능 여부를 더 안전하게 판단할 수 있습니다.

## 11. 보안 Agent는 어떤 기준으로 이체 리스크를 평가하나요?

`SecurityAgent`는 결정론적 rule로 이체 리스크를 평가합니다. 대표 기준은 고액 이체, 야간 고액 이체, 익숙하지 않은 수신자, 짧은 시간 내 반복 이체, 고위험 고객 프로필입니다.

예를 들어 금액이 `otp_threshold` 이상이면 고액 rule이 발동하고, 고객의 `risk_profile`이 `high`이면 100만원 이상 이체에서 OTP를 강제할 수 있습니다. 결과는 `risk_score`, `level`, `triggered_rules`, `warnings`, `force_otp` 형태로 TransferAgent에 반환되고, 확인 카드와 OTP 여부에 반영됩니다.

보완 포인트: 실제 서비스라면 rule 기반에 더해 이상거래탐지 모델, 기기 fingerprint, 위치 정보, 최근 로그인 이력, 수신자 등록 기간 등을 결합해야 합니다.

## 12. 수신자 별칭 학습은 어떻게 동작하나요?

사용자가 "사친", "자기야"처럼 기존 즐겨찾기에 없는 표현을 쓰면 TransferAgent가 되묻기를 통해 실제 수신자를 확인합니다. 사용자가 특정 수신자를 선택하거나 이름을 알려주면 `AliasMemory`에 alias와 recipient_id를 저장하고, 이후 같은 표현이 들어왔을 때 바로 해당 수신자로 해석할 수 있습니다.

이 방식은 자연어 뱅킹에서 중요한 개인화 요소입니다. 사용자는 매번 정확한 등록명을 말하지 않아도 되고, 시스템은 사용자별 표현을 학습할 수 있습니다.

보완 포인트: 잘못 학습된 alias를 수정/삭제하는 UI와, 민감하거나 오해 가능한 alias에 대한 재확인 정책이 있으면 운영 안정성이 높아집니다.

## 13. 추천 Agent는 어떤 방식으로 수신자를 추천하나요?

`RecommendAgent`는 즐겨찾기, 과거 이체 빈도, 최근 이체, 자동이체 같은 데이터를 점수화해 수신자를 추천합니다. 추천 계산은 사용자별로 60초간 `CachePolicy`를 적용해 반복 호출 시 DB 조회와 계산 비용을 줄입니다.

추천은 read-only 성격이므로 Supervisor의 병렬 실행에 잘 맞습니다. 잔액 조회와 동시에 실행해도 DB 상태를 변경하지 않기 때문에 안전합니다.

보완 포인트: 상품추천 Agent나 금융상품 추천으로 확장하려면 단순 빈도 기반 추천뿐 아니라 사용자 동의, 설명 가능성, 적합성 원칙, 투자성 상품 규제 요건까지 고려해야 합니다.

## 14. 현재 A2A 구현에서 TransferAgent 직접 호출을 막은 이유는 무엇인가요?

TransferAgent는 실제 이체 실행으로 이어질 수 있고, 확인과 OTP 같은 Human-in-the-Loop 단계가 필요합니다. 외부 client가 단순 JSON-RPC 한 번으로 TransferAgent를 직접 호출하면 중간 확인 절차를 우회하거나 resume 상태를 제대로 처리하지 못할 수 있습니다.

그래서 현재 A2A route에서는 `transfer` 직접 호출을 거부하고 Supervisor 경유만 허용합니다. Supervisor는 session_id, checkpoint, interrupt payload, 응답 저장을 함께 관리하므로 더 안전합니다.

보완 포인트: 외부 A2A client가 transfer까지 안전하게 사용할 수 있게 하려면 multi-turn task id, pending action 조회, confirm/otp resume API, 인증/인가 정책이 필요합니다.

## 15. Checkpointer를 사용한 이유는 무엇인가요?

Checkpointer는 사용자의 대화 세션별 그래프 상태를 저장하기 위해 사용합니다. 이 프로젝트에서는 SQLite 기반 `SqliteSaver`를 사용하고, `thread_id`를 `user_id:session_id` 형태로 구성합니다.

이체 확인, OTP 입력, 수신자 되묻기처럼 그래프가 중간에 멈추는 경우 다음 요청에서 이전 상태를 이어가야 합니다. Checkpointer가 없으면 pending transfer data, candidate recipients, risk assessment 같은 중간 상태를 별도 세션 저장소에 직접 구현해야 합니다.

보완 포인트: 운영 환경에서는 SQLite 대신 Postgres 같은 외부 DB checkpointer를 검토하고, checkpoint lifecycle과 보존 기간 정책을 명확히 해야 합니다.

## 16. State reducer를 명시한 이유는 무엇인가요?

LangGraph에서 병렬 branch가 같은 state key를 동시에 업데이트할 수 있기 때문입니다. 이 프로젝트는 `_replace`와 `_accumulate` reducer를 명시해 어떤 값은 마지막 값으로 대체하고, 어떤 값은 리스트로 누적합니다.

예를 들어 `agent_results`, `agent_activity`, `node_logs`, `graph_trace`는 병렬 실행 결과가 모두 보존되어야 하므로 accumulate 방식이 필요합니다. 반면 `intent`, `response_type`, `amount` 같은 값은 현재 흐름 기준의 최신 값이 중요하므로 replace 방식이 맞습니다.

보완 포인트: state key가 늘어날수록 reducer 선택 실수가 생길 수 있으므로, state 설계 문서와 branch별 update test를 추가하면 좋습니다.

## 17. 테스트와 시연 관점에서 이 구조의 장점은 무엇인가요?

LLM이 없어도 deterministic mode로 동작하기 때문에 테스트와 시연의 재현성이 높습니다. `tests/`에는 parsing, transfer service, agent 관련 테스트가 있고, `scripts/smoke_test.py`, `scripts/web_smoke.py`, `scripts/a2a_client_demo.py`로 주요 시나리오를 확인할 수 있습니다.

또한 `AgentRunLog`에 plan, activity, node logs, graph trace가 저장되므로 실패했을 때 어느 단계에서 문제가 생겼는지 설명하기 쉽습니다. 시연 중에도 "Supervisor가 왜 이 agent를 호출했는지"를 UI 패널로 보여줄 수 있습니다.

보완 포인트: planner gold set, interrupt resume 시나리오, A2A error case, 보안 rule boundary value test를 더 늘리면 회귀 안정성이 좋아집니다.

## 18. 현재 시스템의 가장 큰 기술적 한계는 무엇인가요?

가장 큰 한계는 데모 목적의 로컬 단일 애플리케이션 구조라는 점입니다. Flask, SQLite, in-memory cache, local checkpoint를 사용하므로 분산 운영, 고가용성, 인증/인가, 권한 분리, 실시간 모니터링은 제한적입니다.

또 다른 한계는 planner와 parser가 아직 제한된 도메인 표현에 최적화되어 있다는 점입니다. 실제 사용자 발화는 훨씬 다양하고, 금융 도메인은 예외 상황이 많습니다.

보완 포인트: 운영화를 위해서는 인증/인가, 감사 로그 불변성, 개인정보 암호화, 비동기 task 처리, 장애 복구, 관측성, 모델 평가 체계를 추가해야 합니다.

## 19. 실제 금융 서비스에 적용하려면 무엇을 보강해야 하나요?

실제 금융 서비스에 적용하려면 현재 데모보다 훨씬 강한 통제가 필요합니다. 대표적으로 본인 인증, 계좌 권한 검증, 수신자 등록 정책, 이상거래탐지, 전자금융거래법 및 내부통제 요건, 개인정보 보호, 감사 로그 보존, 장애 대응이 필요합니다.

또한 LLM 사용 영역을 명확히 제한해야 합니다. LLM이 생성한 설명은 사용자 편의에 도움을 줄 수 있지만, 거래 승인, 수수료 계산, 잔액 차감, OTP 면제 여부 같은 핵심 판단은 검증 가능한 정책 엔진이 담당해야 합니다.

보완 포인트: 금융권 적용을 전제로 한다면 policy engine, approval workflow, immutable audit log, PII masking, prompt/response logging policy를 별도 설계해야 합니다.

## 20. 발표에서 이 프로젝트의 차별점을 한 문장으로 설명한다면 무엇인가요?

"자연어 이체 데모를 단순 챗봇으로 구현한 것이 아니라, Supervisor 기반 multi-agent workflow, A2A discovery/invoke, runtime context, interrupt 기반 Human-in-the-Loop, 결정론적 금융 실행 로직을 결합해 감사 가능하고 확장 가능한 에이전트 구조로 구현했다"라고 설명할 수 있습니다.

핵심 차별점은 LLM을 전면에 세우되 모든 결정을 LLM에 맡기지 않았다는 점입니다. 자연어 이해와 계획은 agent layer가 담당하고, 실제 금융 실행과 보안 판단은 코드와 rule로 통제합니다.

보완 포인트: 발표 자료에는 "LLM이 하는 일"과 "코드가 보장하는 일"을 분리한 표를 넣으면 안정성과 설계 의도를 더 설득력 있게 전달할 수 있습니다.

## 전체 보완 제안 요약

1. Agent registry를 선언형 설정 또는 plugin registry로 분리한다.
2. Agent Card에 `read_only`, `side_effect`, `requires_confirmation` 같은 안전 metadata를 추가한다.
3. Planner 결과에 대한 gold set과 regression test를 만든다.
4. interrupt payload와 response_data를 타입화한다.
5. Transfer A2A를 지원하려면 task id 기반 multi-turn protocol을 추가한다.
6. Checkpointer를 운영용 DB로 전환하고 보존 기간 정책을 정의한다.
7. 보안 rule을 실제 이상거래탐지 feature와 결합한다.
8. AliasMemory 수정/삭제 UI와 오학습 방지 정책을 추가한다.
9. 감사 로그의 불변성, 개인정보 마스킹, 접근 권한 정책을 보강한다.
10. 발표 자료에는 workflow 다이어그램, A2A endpoint, runtime context 분리 표, LLM/결정론 코드 역할 분리 표를 함께 제시한다.
