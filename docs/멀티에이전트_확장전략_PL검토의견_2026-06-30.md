## 0. 한 장 요약 (TL;DR)

- 본 과제는 **3개년 장기 프로젝트**이므로, 처음부터 모든 에이전트를 물리적으로 분리하지 않고 **단계적으로 확장**하는 설계를 제안한다.
- **1년차:** 단일 슈퍼에이전트 중심 파드 1개로 운영한다. 로그·트레이싱·컨텍스트·네트워크(로드밸런싱)를 슈퍼에이전트가 일괄 책임지고, 각 에이전트 담당자는 **표준화된 서비스 규약(Agent Contract)** 위에서 개발한다.
- **2~3년차:** 에이전트를 고도화하고, 개별 호출이 가능한 형태로 **파드를 분리 배포**한다. 슈퍼에이전트도 별도 배포하여 **게이트웨이/오케스트레이터** 역할만 수행하고, 서브에이전트는 A2A·MCP·HTTP로 호출한다.
- **횡단 관심사(감사로그·트레이싱·성능·컨텍스트)는 서브에이전트가 아니라 슈퍼바이저가 통합 관리**하는 방향이 옳다고 본다.
- 다만 **즉시 결정이 필요한 미결 항목**이 있다: ① 슈퍼에이전트 전담 인력 부재(WBS상 '검색 에이전트'에 통합되어 불명확), ② 형상관리/CICD 툴 미정, ③ AWX의 배포·재배포·로드밸런싱 제공 범위 확인, ④ 모노레포 채택 여부, ⑤ 주간 코드 병합 리딩 주체.

> **핵심 메시지:** "지금 당장 마이크로서비스로 쪼개자"가 아니라, **"분리하기 전에 계약(Contract)부터 표준화하고, 1년차는 단일 파드로 빠르게, 2~3년차에 위험도 낮은 에이전트부터 분리하자"** 입니다.

## 1. 왜 단계적 확장인가 (설계 철학)

처음부터 모든 에이전트를 분리 배포하면 다음 부담이 동시에 발생한다.

- **에이전트 경계 확정 부담** — 아직 도메인 책임 범위가 유동적인데 서비스 경계를 먼저 그으면 재설계 비용이 크다.
- **점검·디버깅 부담** — 분산 추적, 서비스 간 호출 실패, 상태 동기화 등 운영 난이도가 초기부터 급증한다.
- **개발 속도 저하** — 소수 인원이 다수 파드를 동시에 띄우고 통합 테스트하는 비용이 비효율적이다.

반대로, 현재 방식 그대로 인원만 늘리면 공통 상태·의존성·테스트·배포 책임이 빠르게 엉킨다.

→ 따라서 **1년차는 단일 파드로 속도를, 계약(Contract) 표준화로 미래 분리를 준비**하고, **2~3년차에 실제 책임·배포 주기가 갈라지는 에이전트부터 분리**하는 것이 가장 안전하다. (근거 문서 §1, §10과 동일한 결론)

## 2. 1년차 목표 구조 — 단일 슈퍼에이전트 파드

```
화면/백엔드
    ↓ (슈퍼에이전트만 호출)
┌─────────────────────────────────────────┐
│  단일 파드 (Pod)                          │
│  ┌───────────────────────────────────┐  │
│  │ Global Supervisor                  │  │
│  │  - 플래닝 / 라우팅 / 결과 취합       │  │
│  │  - 로그·트레이싱·컨텍스트 일괄 관리   │  │
│  └───────────────────────────────────┘  │
│   ↓ subgraph 호출 (in-process)           │
│  [이체] [조회] [추천] [보안] [메뉴] [상품] [계산]│
└─────────────────────────────────────────┘
```

**1년차에 슈퍼에이전트가 일괄 책임지는 것**

| 영역 | 1년차 처리 방식 |
|---|---|
| 로그 관리 | 슈퍼에이전트가 표준 포맷으로 중앙 집계 |
| 트레이싱 | 단일 trace_id로 Supervisor→Sub-Agent 전 구간 연결 |
| 컨텍스트 관리 | 세션/대화 상태를 슈퍼에이전트가 보관·전달 |
| 네트워크/로드밸런싱 | 파드 단위 스케일링(아직 에이전트별 분리 불필요) |

**이 구조의 장점**

- 모든 에이전트 담당 개발자가 **동일한 서비스 규약(입력/출력 envelope, Agent Card, 테스트 책임)** 위에서 구현 → 표준화 효과.
- 분산 추적·서비스 메시 없이도 디버깅이 단순.
- 1년차에 만든 **계약(Contract)** 이 2~3년차 분리의 인터페이스가 그대로 된다.

> **[내 의견]** 1년차의 진짜 산출물은 "동작하는 에이전트"뿐 아니라 **"분리 가능한 계약"** 이어야 한다. 즉, 코드는 한 파드에 있어도 **내부 경계는 이미 분리된 것처럼** 설계한다.

## 3. 2~3년차 목표 구조 — 게이트웨이 + 서브에이전트 분리

```
화면/백엔드
    ↓ (여전히 슈퍼에이전트만 호출 — 단일 진입점 유지)
┌──────────────────────────┐
│ Super-Agent (별도 파드)    │  ← 게이트웨이 + 오케스트레이터
│  - 플래닝                  │
│  - 컨텍스트/트레이싱 통합 관리 │
│  - 감사로그 통합            │
└──────────────────────────┘
   ↓ A2A / MCP / HTTP (클라이언트 입장에서 호출)
 ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
 │이체 파드 │ │메뉴 파드 │ │계산 파드 │ │ … 파드   │
 └─────────┘ └─────────┘ └─────────┘ └─────────┘
```

**핵심 설계 원칙**

1. **단일 진입점 유지** — 화면 백엔드는 2~3년차에도 슈퍼에이전트만 호출한다. 서브에이전트 분리는 내부 구현 변화이지 외부 인터페이스 변화가 아니어야 한다.
2. **슈퍼에이전트는 도메인 판단을 흡수하지 않는다** — 계산식 검증, 검색 컬렉션 선택 등은 각 서브에이전트 책임. 슈퍼는 "누구를 부를지 / 결과를 어떻게 합칠지 / 한계를 어떻게 설명할지"에 집중.
3. **프로토콜은 용도별 선택** — A2A(에이전트 간 표준 호출), MCP(외부 AI 클라이언트/AWX 연동), HTTP(내부 단순 호출)를 **혼용**하되 슈퍼에이전트 쪽 어댑터로 추상화한다.

### 분리 우선순위 (위험도 기반)

| 순위 | 대상 | 근거 |
|---|---|---|
| 먼저 | 금융계산기, 메뉴탐색, 상품안내 | side effect 낮음(읽기/계산/RAG), 독립 테스트 쉬움 |
| 나중 | **이체 에이전트** | 금전 이동 + HITL/OTP/멱등성/보안협업 얽힘 → 기준 구현으로 두고 **마지막에** 분리 |

> **[내 의견]** "슈퍼에이전트를 어떻게 분리할까"에 대한 답: **슈퍼에이전트는 도메인 로직을 0으로 유지**해야 분리가 깔끔하다. 1년차부터 슈퍼에이전트 안에 이체/계산 로직이 섞이지 않게 관리하는 것이 2~3년차 분리의 성패를 가른다.

## 4. 횡단 관심사(감사·트레이싱·성능·컨텍스트)는 누가 관리하나

**고민:** 각 서브에이전트가 자기 것을 관리할지, 슈퍼바이저가 통합할지.

> **[내 의견 — 슈퍼바이저 통합이 맞다]**

| 관심사 | 관리 주체 | 이유 |
|---|---|---|
| 감사 로그 | **슈퍼바이저 통합** | 규제 대응·전 구간 추적은 한 곳에서 봐야 함 |
| 트레이싱 | **슈퍼바이저가 trace_id 발급/연결** | 분리 후에도 trace 끊김 방지 |
| 컨텍스트/세션 | **슈퍼바이저 보관, 서브로 전달** | 서브에이전트는 stateless에 가깝게 |
| 에이전트 성능 | **슈퍼바이저 집계 + 서브가 메트릭 방출** | 서브는 latency/status/error_type만 표준 필드로 보고, 통합은 슈퍼 |

→ **원칙:** 서브에이전트는 **표준 관측 필드(agent_id, version, latency, status, error_type)를 방출**만 하고, **수집·통합·보존은 슈퍼바이저**가 한다. 분리 배포 시 trace 단절을 막는 핵심이다.

## 5. 개방형 생태계 — 타팀 호출 / 외부 에이전트 부착

**목표 방향성(가능하면 좋음):** 다른 부서·팀이 우리 에이전트를 개별 단위로 호출하거나, 우리가 외부 에이전트를 붙이는 양방향 확장.

가능하게 하려면 다음을 미리 설계해야 한다.

- **표준 호출 규약** — A2A Agent Card + `/invoke` 표준 엔드포인트(메타데이터/호출/헬스)를 공개 계약으로 관리.
- **인증·권한 경계** — 타팀 호출 시 인증 토큰, 호출 허용 범위(allowlist), 감사 추적.
- **side-effect 정책** — 외부에서 호출하더라도 **실행 권한은 우리 애플리케이션 policy가 최종 통제**(특히 이체). MCP tool description이 실행 권한을 결정하게 두면 안 됨.
- **버전 호환성** — agent_version 명시, 하위 호환 깨질 때 계약 테스트로 차단.

> **[내 의견]** 양방향 개방은 충분히 가능하나, **1년차에는 "내부 표준 계약"만 잡고 외부 공개는 2~3년차로** 미루는 것이 안전하다. 계약이 흔들리는 상태에서 외부에 노출하면 호환성 부채가 쌓인다.

## 6. 조직·역할 이슈 — 슈퍼에이전트 전담자 부재 (★ 의사결정 필요)

**현재 WBS의 공백:** 슈퍼에이전트는 플래닝·컨텍스트·트레이싱·결과 취합·전 구간 감사라는 **가장 무거운 책임**을 지는데, **전담 담당자가 별도로 없다.** 현재 '검색 에이전트'라는 이름에 통합되어 있어 책임 경계가 불명확하다.

- 슈퍼에이전트는 단순 라우터가 아니라 **시스템 전체의 신뢰성·관측성·오케스트레이션을 책임지는 핵심 컴포넌트**다.
- 각 도메인 에이전트 담당자와는 **역할 성격이 다르다**(플랫폼/공통 성격).

> **[내 의견]** 슈퍼에이전트는 **'검색 에이전트' 담당과 분리**하여, **플랫폼/공통 담당(또는 PL 직속 1명)** 으로 명시해야 한다. 횡단 관심사(로그·트레이싱·컨텍스트 표준)를 정의·유지하는 역할이므로 도메인 담당과 겸임시키면 표준이 흔들린다.

**역할 분담 제안**

| 역할 | 책임 |
|---|---|
| 슈퍼에이전트 담당(신설) | 플래닝, 라우팅, 공통 envelope/Contract, 트레이싱·감사 통합, 레지스트리 |
| 각 도메인 에이전트 담당 | 자기 도메인 로직·데이터·정책·단위테스트·계약테스트 |
| PL | 계약 표준 합의 주재, 병합 관리 리딩, 분리 시점 판단 |

## 7. 인프라·운영 미결정 사항 (★ AWX 확인 필요)

PL 입장에서 다음 항목은 **AWX(Agentic Works, 자사 AI 플랫폼)의 제공 범위를 먼저 확인**해야 결정 가능하다.

| 항목 | 현재 상태 | 확인/결정 필요 사항 |
|---|---|---|
| 형상관리/CICD | 미정 (GitLab 등 후보) | AWX가 코드 형상관리·파이프라인을 제공하는지, 외부 GitLab 연동인지 |
| 주간 코드 병합 | 미정 | 매주 정해진 시간 병합 관리의 **리딩 주체** (PL이 가능한지 포함) |
| 로드밸런싱 | 미정 | 파드 레벨 LB를 AWX가 제공하는지, 별도 구성인지 |
| 재배포 방식 | 미정 | 재배포 시 **AWX 전체를 내려야 하는지**, 무중단(롤링) 배포 가능한지 |
| 모노레포 vs 멀티레포 | 미정 | 에이전트 분리 배포와 모노레포가 양립 가능한지 |

> **[내 의견 / 방향성]**
> - **형상관리:** AWX가 제공하는 방식을 우선 확인하고, 미제공 시 GitLab로 통일. **이건 AWX 담당에게 별도 문의 필요.**
> - **주간 병합 리딩:** PL이 **병합 정책과 리뷰 게이트**는 책임지되, 실제 머지 실행은 슈퍼에이전트 담당과 분담 가능. PL이 못 할 일은 아니나 **단독 부담은 피해야** 함.
> - **재배포:** "재배포마다 AWX 전체 다운"은 운영상 치명적 → **무중단 배포 가능 여부가 분리 배포의 전제 조건.** 불가하면 1년차 단일 파드 유지 근거가 더 강해짐.
> - **모노레포:** 초기엔 **모노레포 + 폴더별 에이전트**가 표준 계약 공유에 유리. 2~3년차 분리 배포 시점에 파드별 빌드 타깃만 나누면 모노레포와 분리 배포는 양립 가능. → **모노레포 채택 권고.**

| D4 | 주간 병합 리딩 주체 | PL이 정책 책임 + 실행 분담 |
| D5 | 모노레포 채택 여부 | **모노레포 권고** |
| D6 | AWX 배포/재배포/LB 제공 범위 공식 확인 | AWX 담당 회신 필요 |

## 9. 향후 투입 시 점검 체크리스트

분리·확장 단계 진입 전 반드시 점검할 항목.

- [ ] **계약 표준** — 공통 응답 envelope(status, agent_id, version, side_effect_level, requires_user_confirmation, error) 확정?
- [ ] **Agent Card** — owner / responsibilities / not_responsible_for / side_effect_level / 계약테스트 경로 명시?
- [ ] **레지스트리** — 신규 에이전트 추가 시 한 곳만 수정하면 planner·라우팅·A2A·테스트가 파생되는가?
- [ ] **트레이싱** — 분리 배포 후에도 단일 trace_id로 전 구간 연결되는가?
- [ ] **이체 분리 전제** — 세션 resume / idempotency key / 승인 전후 상태 분리 / 감사로그 양방향 trace 연결 준비?
- [ ] **재배포** — 무중단 배포 가능? AWX 다운 없이 파드 단위 롤링 가능?
- [ ] **slot/cp949/SSL 환경** — 분리 배포 시 인코딩·인증서 환경이 각 파드에 일관 적용되는가?
- [ ] **권한 경계** — 외부/타팀 호출 시 실행 권한이 애플리케이션 policy로 최종 통제되는가?

## 10. 결론

본 과제는 멀티에이전트 구조를 **새로 도입할 단계가 아니라, 이미 구현된 MVP를 3개년 팀 개발 구조로 정리할 단계**다.

- **1년차:** 단일 슈퍼에이전트 파드 + 계약 표준화 (속도 + 미래 분리 준비)
- **2~3년차:** 위험도 낮은 에이전트부터 분리 배포, 슈퍼에이전트는 게이트웨이화
- **횡단 관심사:** 슈퍼바이저 통합 관리
- **즉시 해결 필요:** 슈퍼에이전트 전담자 신설, AWX 운영 범위(형상관리·재배포·LB) 공식 확인

> **한 문장 요약:** "지금 쪼개지 말고, **먼저 계약을 표준화하고 1년차는 단일 파드로 빠르게 가되, 슈퍼에이전트 전담자와 AWX 운영 범위만 지금 확정**하면, 2~3년차 분리는 인터페이스 변경 없이 안전하게 진행할 수 있습니다."
