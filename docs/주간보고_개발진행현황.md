# AI Banking Transfer Agent 개발 진행현황 주간보고

> 보고일: 2026-06-11  
> 프로젝트: `ai-banking-transfer-agent`  
> 보고 목적: 현재까지의 개발 진행현황을 기술 구조, 업무 흐름, 시나리오, 데이터 관점에서 공유하고 차주 고도화 방향을 정리

---

## 1. 요약

이번 주에는 개인뱅킹 송금 업무를 대상으로 한 **AI Banking Transfer Agent**의 핵심 구조와 주요 데모 시나리오를 구현했습니다. 사용자가 자연어로 송금, 조회, 추천을 요청하면 Supervisor Agent가 실행 계획을 세우고, 역할별 Sub-Agent가 송금 실행, 잔액/이력 조회, 수취인 추천, 보안 판단을 분담하는 구조입니다.

현재 구현은 단순 챗봇 응답이 아니라, 금융 업무에 필요한 **확인, 모호성 해소, OTP, 보안 룰, 실행 로그**를 포함하는 워크플로우형 Agent 구조를 지향합니다. LLM은 의도 분류, 계획 수립, 응답 표현 보조에 활용하고, 실제 송금 판단과 실행은 결정론적 서비스 코드와 DB 트랜잭션으로 통제하는 방향으로 설계했습니다.

차주부터는 데이터 현실성 강화, 보안 룰 고도화, Planner 평가 자동화, A2A 확장, 관리자 로그/trace 개선을 중심으로 고도화할 예정입니다.

## 3. 현재 시스템 구조

현재 시스템은 Flask 기반 웹 UI와 LangGraph 기반 Agent Orchestration 구조로 구성되어 있습니다.

```text
사용자 자연어 요청
        |
        v
Supervisor Agent
- 사용자 의도 분석
- 실행 계획 수립
- 필요한 Sub-Agent 선택
- 결과 취합 및 응답 생성
        |
        +--> TransferAgent
        |    - 수취인/금액 추출
        |    - 수취인 모호성 해소
        |    - 확인/OTP/송금 실행
        |
        +--> InquiryAgent
        |    - 잔액 조회
        |    - 이체내역 조회
        |    - 정기이체 조회
        |
        +--> RecommendAgent
        |    - 자주 보내는 사람 추천
        |    - 최근 이체 기반 추천
        |    - 정기이체 기반 제안
        |
        +--> SecurityAgent
             - 고액 송금 판단
             - 위험도 평가
             - OTP 필요 여부 판단
```

### 핵심 설계 방향

| 설계 항목 | 적용 방향 |
|---|---|
| Agent 분리 | 송금, 조회, 추천, 보안 판단을 역할별 Agent로 분리 |
| Supervisor 구조 | 사용자의 자연어 요청을 실행 계획으로 변환 후 적절한 Agent 호출 |
| 결정론적 실행 | 실제 송금, 잔액 차감, OTP 판단 등은 Python 서비스 코드로 통제 |
| LLM 활용 범위 제한 | 자연어 해석, 계획 수립, 응답 문장 보정에 제한적으로 활용 |
| 상태 유지 | Checkpointer를 통해 확인/OTP/모호성 해소 등 중간 상태 유지 |
| 감사 가능성 | Agent 실행 계획, node log, graph trace를 기록하여 판단 근거 추적 |

## 4. 기술 관점 진행현황

### 4.1 LangGraph 기반 워크플로우

금융 송금 업무는 단순 질의응답보다 순서와 상태가 중요합니다. 따라서 LangGraph를 사용해 송금 업무를 명시적인 workflow로 구성했습니다.

주요 적용 요소는 다음과 같습니다.

| 기술 요소 | 적용 내용 | 기대 효과 |
|---|---|---|
| `StateGraph` | Agent별 처리 흐름을 graph 형태로 구성 | 업무 흐름 명확화 |
| `Runtime Context` | 사용자 ID, 고객 등급, LLM 설정, OTP 기준 등 실행 환경 주입 | 테스트 및 A2A 호출 용이 |
| `Command` | 다음 node 또는 parent graph로 흐름 제어 | 확인 중 다른 요청 처리 가능 |
| `Send` | 조회와 추천처럼 독립적인 작업을 병렬 실행 | 응답 속도 및 확장성 개선 |
| `interrupt` | 확인, OTP, 금액 누락, 수취인 모호성 처리 | Human-in-the-Loop 구현 |
| Checkpointer | 세션별 graph 상태 저장 | 멀티턴 대화 유지 |
| Reducer | 병렬 Agent 결과 누적 및 응답 취합 | fan-out 결과 안정적 병합 |

### 4.2 Supervisor/Sub-Agent 구조

Supervisor는 “무엇을 처리할지”를 판단하고, Sub-Agent는 “어떻게 처리할지”를 담당합니다. 이 구조를 통해 신규 Agent를 추가하더라도 기존 송금 로직에 미치는 영향을 줄일 수 있습니다.

예를 들어 향후 `ProductRecommendAgent`, `BudgetAnalysisAgent`, `FraudDetectionAgent`를 추가할 경우 Supervisor의 planning 대상과 Agent registry를 확장하는 방식으로 대응할 수 있습니다.

### 4.3 A2A 확장 기반

현재 내부적으로는 LangGraph의 node/subgraph 호출 구조를 사용하고, 외부적으로는 Agent Card와 JSON-RPC 형태의 호출 구조를 마련했습니다. 이를 통해 향후 각 Agent를 별도 서비스 또는 외부 Agent와 연동하는 구조로 확장할 수 있습니다.

현재 A2A 적용 범위는 다음과 같습니다.

| 항목 | 내용 |
|---|---|
| Agent Card | Agent 이름, 역할, 기능 메타데이터 제공 |
| Agent 목록 API | 사용 가능한 Sub-Agent 목록 조회 |
| Agent invoke API | JSON-RPC 형태로 Agent 호출 |
| 현재 제한 | Human-in-the-Loop가 필요한 TransferAgent 직접 호출은 제한적으로 운영 필요 |

## 5. 업무 흐름 관점 진행현황

현재 송금 Agent는 다음 흐름으로 동작합니다.

```text
1. 사용자 요청 입력
2. Supervisor가 의도 분석 및 실행 계획 생성
3. TransferAgent가 수취인/금액 추출
4. 수취인 모호성 또는 금액 누락 시 사용자에게 추가 질문
5. SecurityAgent가 금액/위험도/OTP 필요 여부 판단
6. 사용자 확인 카드 생성
7. 필요 시 OTP 입력 요청
8. TransferService가 DB 트랜잭션으로 송금 실행
9. 실행 결과 및 Agent 판단 로그 저장
10. 사용자에게 최종 응답
```

이 흐름에서 중요한 점은 사용자의 자연어 요청이 곧바로 실행되지 않는다는 것입니다. 송금과 같이 위험도가 높은 업무는 반드시 검증, 확인, 보안 판단 단계를 거친 뒤 실행되도록 구성했습니다.

## 6. 대표 시나리오

### 6.1 기본 송금

사용자 요청:

```text
엄마에게 5만원 보내줘
```

처리 흐름:

```text
수취인 "엄마" 해석
금액 50,000원 추출
잔액/한도 확인
보안 위험도 평가
확인 카드 생성
사용자 확인 후 송금 실행
```

### 6.2 수취인 모호성 해소

사용자 요청:

```text
민수에게 5만원 보내줘
```

처리 흐름:

```text
"민수" 후보 2명 이상 탐색
후보 목록 제시
사용자 선택
선택 결과를 별칭/선호 데이터로 학습
이후 동일 표현 사용 시 바로 해석
```

### 6.3 금액 누락 보완

사용자 요청:

```text
지훈이한테 보내줘
```

처리 흐름:

```text
수취인은 해석되지만 금액 누락
Agent가 금액 질문
사용자가 "3만원" 입력
기존 context와 결합하여 송금 확인 단계 진행
```

### 6.4 확인 중 수정 요청

사용자 요청:

```text
엄마에게 5만원 보내줘
```

확인 단계에서 사용자 입력:

```text
아니 3만원으로 바꿔줘
```

처리 흐름:

```text
기존 송금 대기 상태 유지
금액만 30,000원으로 갱신
확인 카드 재생성
```

### 6.5 조회와 추천 병렬 실행

사용자 요청:

```text
잔액 보여주고 자주 보내는 사람 추천해줘
```

처리 흐름:

```text
Supervisor가 inquiry + recommend 실행 계획 생성
InquiryAgent와 RecommendAgent 병렬 실행
각 결과 취합
하나의 응답으로 사용자에게 제공
```

### 6.6 고액 송금 OTP

사용자 요청:

```text
집주인한테 400만원 보내줘
```

처리 흐름:

```text
금액 4,000,000원 추출
SecurityAgent가 고액 송금 rule 감지
OTP 필요 판단
사용자 확인 후 OTP 요청
OTP 검증 후 송금 실행
```

## 7. 데이터 관점 진행현황

현재 데이터는 데모 목적의 목업 데이터이지만, 실제 개인뱅킹 사용 패턴을 반영할 수 있도록 구성했습니다.

| 데이터 영역 | 활용 목적 |
|---|---|
| 사용자 | 고객별 프로필, 등급, 위험도, 나이 기반 응답 차별화 |
| 계좌 | 출금 계좌, 잔액, 계좌 유형 관리 |
| 수취인 | 가족, 친구, 모임, 임대인 등 개인 관계 기반 송금 |
| 즐겨찾기 | 자주 보내는 사람 빠른 추천 |
| 별칭 메모리 | "사친", "집주인" 같은 사용자 표현 학습 |
| 이체 이력 | 최근 송금, 반복 패턴, 추천 근거 |
| 정기이체 | 월세, 관리비, 회비 등 반복 송금 추천 |
| 보안 룰 | 금액, 고객 위험도, 신규 수취인 등 OTP 판단 |
| Agent 로그 | 실행 계획, Agent 호출, 판단 근거 추적 |

데이터 측면에서 현재 강점은 “데모 시나리오별로 설명 가능한 근거 데이터”가 있다는 점입니다. 다만 실서비스 수준으로 가기 위해서는 거래 패턴의 다양성, 이상거래 데이터, 사용자별 선호 데이터, 실패 케이스 데이터가 추가로 필요합니다.

향후에는 Planner 평가셋과 보안 rule boundary test를 추가하여, 자연어 입력이 다양해져도 Agent 선택과 송금 통제가 안정적으로 유지되는지 검증할 계획입니다.

## 9. 현재 한계 및 리스크

| 영역 | 현재 한계 | 대응 방향 |
|---|---|---|
| 인증/권한 | 실제 금융 인증, 계좌 권한 검증 미연동 | 인증/권한 mock을 실제 정책 구조에 가깝게 확장 |
| 데이터 | 목업 데이터 중심 | 거래 패턴, 실패 케이스, 이상거래 데이터 보강 |

| 보안 | 기본 rule 중심 | 신규 수취인, 시간대, 반복 이체, 위험 고객 rule 확장 |
| 운영성 | 로컬 Flask/SQLite 중심 | 배포 구조, DB 전환, 로그 보존 정책 검토 |
| A2A | 장기 실행 task/resume protocol 제한 | task id, status 조회, callback/streaming 설계 필요 |
| 관측성 | 로그는 있으나 운영 대시보드 수준은 아님 | Agent trace, decision reason, error summary 화면 개선 |

## 10. 차주 고도화 계획

### 10.1 Planner 평가 자동화

사용자 발화 50~100개 수준의 평가셋을 만들고, 각 발화에 대해 기대되는 intent, 호출 Agent, 필요 slot, 보안 여부를 정의합니다. 이를 통해 Supervisor가 잘못된 Agent를 호출하거나 송금성 요청을 조회성 요청으로 오판하는 문제를 조기에 발견할 수 있습니다.

예상 산출물:

| 산출물 | 내용 |
|---|---|
| Planner gold set | 발화별 기대 intent/Agent/slot 정의 |
| Regression test | Planner 변경 시 기존 시나리오 유지 여부 검증 |
| 실패 케이스 리포트 | 오분류 발화와 개선 필요 rule 정리 |

### 10.2 보안 룰 고도화

현재 고액 송금과 고객 위험도 중심의 보안 판단을 다음 기준으로 확장합니다.

| 보안 기준 | 설명 |
|---|---|
| 신규 수취인 | 처음 보내는 사람에게 일정 금액 이상 송금 시 추가 확인 |
| 반복 송금 | 짧은 시간 내 동일/유사 금액 반복 송금 감지 |
| 시간대 | 심야 시간대 고액 송금 시 추가 경고 |
| 고객 위험도 | 위험 고객군에 대해 OTP 기준 강화 |
| 최근 실패 이력 | OTP 실패 또는 취소 이력이 많은 경우 추가 확인 |

### 10.3 데이터 고도화

데모 데이터의 현실성을 높이기 위해 사용자 유형과 거래 패턴을 확장합니다.

| 데이터 항목 | 고도화 방향 |
|---|---|
| 사용자 | 일반/VIP/고령/위험 고객군 추가 |
| 수취인 | 가족, 친구, 임대인, 모임, 거래처 등 관계 다양화 |
| 이체 이력 | 6개월 이상 반복 패턴과 비정기 송금 혼합 |
| 정기이체 | 월세, 관리비, 회비, 적금, 보험료 등 확대 |
| 별칭 | 사용자별 자연어 표현과 학습 이력 추가 |
| 실패 케이스 | 잔액 부족, 한도 초과, OTP 실패, 수취인 모호성 데이터 추가 |

### 10.4 Agent 로그 및 관리자 화면 개선

현재 Agent 실행 로그를 기반으로 다음 정보를 더 명확히 보여주는 방향으로 개선합니다.

| 개선 항목 | 설명 |
|---|---|
| 실행 계획 표시 | Supervisor가 어떤 계획을 세웠는지 표시 |
| Agent 호출 순서 | 어떤 Sub-Agent가 어떤 순서로 호출되었는지 표시 |
| 보안 판단 근거 | OTP가 필요한 이유와 발동 rule 표시 |
| state 변화 | 송금 대기, 확인, OTP, 실행 완료 상태 변화 표시 |
| 오류 요약 | 실패 원인과 복구 가능 여부 표시 |

### 10.5 A2A 구조 확장

향후 Agent를 별도 서비스로 분리하거나 외부 Agent와 연동할 수 있도록 A2A 구조를 보강합니다.

| 개선 항목 | 설명 |
|---|---|
| Agent registry | Agent 목록과 capability를 코드 상수에서 registry 구조로 분리 |
| task id | 장기 실행 또는 확인 대기 task 식별자 도입 |
| status API | 외부 client가 pending/running/completed 상태 조회 |
| resume API | 확인/OTP 입력을 외부 client가 이어서 처리 |
| streaming/callback | Agent 실행 중간 결과 전달 구조 검토 |

## 11. 보고 시 강조할 메시지

이번 주 진행사항은 단순히 송금 챗봇을 구현한 것이 아니라, **금융 업무에 필요한 안전한 Agent 실행 구조의 기반을 만든 것**입니다.

특히 다음 세 가지를 강조하면 좋습니다.

1. **LLM에 실행을 맡기지 않고 통제 가능한 workflow로 구성**
   자연어 해석과 응답 표현에는 AI를 활용하되, 실제 송금 실행과 보안 판단은 결정론적 코드로 제어합니다.

2. **Supervisor/Sub-Agent 구조로 확장성 확보**
   송금, 조회, 추천, 보안 역할을 분리했기 때문에 향후 상품 추천, 소비 분석, 이상거래 탐지 Agent를 추가하기 쉽습니다.

3. **시나리오와 데이터 기반으로 데모 가능**
   기본 송금, 수취인 모호성, 금액 누락, OTP, 조회/추천 병렬 실행 등 팀장님께 보여드릴 수 있는 흐름이 준비되어 있습니다.

## 13. 결론

현재 프로젝트는 개인뱅킹 송금 Agent의 핵심 구조와 대표 업무 흐름을 구현한 상태입니다. 사용자의 자연어 요청을 Supervisor가 계획으로 변환하고, Sub-Agent가 역할별로 처리하며, 송금 업무에 필요한 확인, OTP, 보안 판단, 로그 추적까지 포함했습니다.

차주부터는 기능 추가보다 **안정성, 검증 가능성, 데이터 현실성, 운영 관측성**을 중심으로 고도화하는 것이 적절합니다. 이를 통해 현재 데모 수준의 Agent를 실서비스 검토가 가능한 구조로 발전시킬 수 있습니다.
