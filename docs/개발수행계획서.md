## 2. 목표 아키텍처

### 2.1 하이라키 구조 (Supervisor + 4 Sub-Agents)

```
                       ┌──────────────────────────────┐
 사용자 메시지 ───────▶│  Supervisor (Leader) Agent    │◀── Runtime Context
                       │  · LLM Planning (실행 계획)   │    (user_id, llm, db,
                       │  · Command 기반 핸드오프      │     risk_profile …)
                       │  · Send 기반 동적 병렬 분기   │
                       └──────┬───────┬───────┬───────┘
              ┌───────────────┤       │       ├────────────────┐
              ▼               ▼       │       ▼                ▼
      ┌──────────────┐ ┌───────────┐ │ ┌──────────────┐ ┌──────────────┐
      │ TransferAgent│ │InquiryAgent│ │ │ RecommendAgent│ │SecurityAgent │
      │ 슬롯추출      │ │ 잔액조회    │ │ │ 추천/지난번    │ │ OTP·한도      │
      │ 수신자해석    │ │ 이체내역    │ │ │ 정기이체 제안  │ │ 사기탐지       │
      │ 이체실행      │ │ 정기이체    │ │ │              │ │ 리스크스코어   │
      └──────┬───────┘ └───────────┘ │ └──────────────┘ └──────▲───────┘
             │                        │                         │
             └── A2A 협업: 이체 검증 요청 ──────────────────────┘
                 (TransferAgent → SecurityAgent 핸드오프)
```

- **Supervisor**: 사용자 의도를 분석해 **실행 계획(Plan)을 LLM이 구조화 출력(Pydantic)으로 생성** → 계획에 따라 Sub-Agent를 순차(Command) 또는 병렬(Send)로 디스패치 → 결과 집계(reduce) 후 응답 합성.
- **병렬 시나리오 예**: "잔고 알려주고, 보낼 만한 곳 추천해줘" → Supervisor가 `Send("inquiry", …)` + `Send("recommend", …)` 동시 fan-out → 결과 병합.
- **협업 시나리오 예**: "집주인한테 500만원" → TransferAgent가 검증 단계에서 `Command(goto="security")`로 SecurityAgent에 위임 → 리스크 스코어/OTP 필요 여부를 받아 이어서 진행.
- **금융 안전 원칙 유지**: Planning과 자연어 이해만 LLM이 담당, 이체 실행·한도 검증·리스크 판정은 기존 결정론적 서비스 레이어를 그대로 호출.

### 2.2 적용할 LangGraph 1.x 최신 기능 (현행화 포인트)

| 기능 | 용도 | 시연 효과 |
|------|------|-----------|
| **Runtime + `context_schema`** | user_id, LLM 핸들, DB, 사용자 등급 등 **불변 의존성 주입** | §3 상세 — 이번 실습의 학습 핵심 |
| **`Command(goto=…, update=…)`** | Supervisor↔Sub-Agent **핸드오프**(A2A 내부 구현) | 에이전트가 다음 에이전트를 동적으로 지목 |
| **`Send` API** | 계획 기반 **동적 병렬 fan-out / map-reduce** | Sub-Agent 동시 실행 |
| **`interrupt()` + `Command(resume=…)`** | 이체 확인·OTP·모호성 해소를 정식 **Human-in-the-Loop**로 전환 | `pending_state` 수동 플래그 제거 |
| **Checkpointer (`SqliteSaver`)** | `state_json` 수동 직렬화 → **공식 영속화 + durable execution** | 중단/재개, 타임트래블 디버깅 |
| **Store (장기 메모리)** | 사용자 선호(자주 보내는 사람, 호칭) 세션 간 기억 | "또 엄마한테" 류 개인화 |
| **Structured Output (Pydantic)** | Supervisor Plan, 슬롯 추출 결과 스키마 강제 | 안정적 라우팅 |
| **`CachePolicy` 노드 캐싱** | 잔액/즐겨찾기 조회 노드 캐싱 | 성능 + 최신 기능 시연 |
| **Subgraph 합성** | 각 Sub-Agent를 독립 `StateGraph`로 컴파일 후 상위 그래프 노드로 장착 | 진짜 계층(hierarchy) 구조 |
| **A2A 프로토콜 (`a2a-sdk`)** | Sub-Agent를 Agent Card로 외부 노출 | 표준 프로토콜 데모 |

### 2.3 Dynamic Prompting 설계

프롬프트를 정적 문자열이 아니라 **Runtime Context + State + Store를 조합해 매 호출 시점에 동적 조립**:

```python
def build_supervisor_prompt(state: SupervisorState, runtime: Runtime[BankingContext]) -> str:
    ctx = runtime.context
    parts = [BASE_PLANNER_PROMPT]
    parts.append(f"고객 등급: {ctx.customer_tier} / 일일 한도 잔여: {ctx.remaining_daily_limit:,}원")
    if ctx.risk_profile == "high":
        parts.append("이 고객은 최근 이상거래 이력이 있으므로 SecurityAgent 검증을 반드시 계획에 포함하라.")
    if prefs := runtime.store.get(("user", str(ctx.user_id)), "preferences"):
        parts.append(f"사용자 선호: {prefs.value}")
    parts.append(f"가용 Sub-Agent 목록: {render_agent_cards(ctx.available_agents)}")
    return "\n\n".join(parts)
```

- 사용자 등급/리스크/한도 등 **상황에 따라 지시문 자체가 달라지는** 구조 → "Dynamic Prompting" 요건 충족.
- Sub-Agent 목록을 Agent Card(이름·능력·입출력 스키마) 형태로 프롬프트에 주입 → A2A의 discovery 개념을 내부에서도 동일하게 사용.

## 3. LangGraph Runtime 이해하기 (학습 가이드)

> 이번 고도화에서 **모든 노드가 Runtime을 통해 의존성을 받도록** 리팩토링한다. 아래는 그 근거와 동작 원리.

### 3.1 Runtime이란?

LangGraph 1.x의 `Runtime`은 그래프 실행 중 노드에 주입되는 **실행 환경 핸들**이다. 핵심 구분:

| 구분 | State | Runtime Context |
|------|-------|-----------------|
| 성격 | **가변** — 노드가 읽고 갱신하는 대화 데이터 | **불변** — 한 번의 invoke 동안 고정된 의존성/설정 |
| 예시 | intent, amount, 검증 결과 | user_id, LLM 클라이언트, DB 세션, 고객 등급 |
| 전달 | 노드 반환값으로 병합 | `graph.invoke(state, context=…)` 로 주입 |
| 체크포인트 | 저장됨 | 저장 안 됨 (매 호출 새로 주입) |

지금까지 이 프로젝트는 `user_id`를 State에 섞어 두었는데, 이는 "대화 데이터"와 "실행 환경"이 뒤섞인 구조다. Runtime 도입으로 분리한다.

### 3.2 사용 패턴 (이번 프로젝트 적용 형태)

```python
from dataclasses import dataclass
from langgraph.graph import StateGraph
from langgraph.runtime import Runtime

@dataclass
class BankingContext:                 # ① context_schema 정의
    user_id: int
    session_id: str
    llm_provider: str                 # "openai" | "none"(rule-based 폴백)
    customer_tier: str = "standard"
    risk_profile: str = "normal"

def classify_intent(state: TransferState, runtime: Runtime[BankingContext]) -> dict:
    llm = get_llm(runtime.context.llm_provider)          # ② context로 의존성 접근
    runtime.stream_writer({"node": "classify_intent"})    # ③ 커스텀 스트리밍
    prefs = runtime.store.get(("user", str(runtime.context.user_id)), "preferences")  # ④ 장기 메모리
    ...

graph = (
    StateGraph(TransferState, context_schema=BankingContext)  # ⑤ 그래프에 스키마 등록
    .add_node(classify_intent)
    ...
    .compile(checkpointer=SqliteSaver(...))
)

# ⑥ 호출 시 context 주입 — State와 분리되어 전달됨
graph.invoke(
    {"current_message": "엄마한테 5만원"},
    config={"configurable": {"thread_id": session_id}},
    context=BankingContext(user_id=1, session_id=sid, llm_provider="openai"),
)
```

`Runtime`이 노드에 제공하는 것: `runtime.context`(불변 의존성), `runtime.store`(스레드를 넘는 장기 메모리), `runtime.stream_writer`(커스텀 스트림 이벤트). 과거의 `config["configurable"]` 딕셔너리 파기 패턴을 **타입 안전하게 대체**하는 것이 Runtime의 존재 이유다.

### 3.3 이 프로젝트에서 Runtime이 해결하는 문제 3가지

1. **Flask 결합 제거** — 현재 노드들이 `current_app.config`를 직접 읽는 부분을 `runtime.context`로 대체 → 에이전트 패키지가 Flask 없이도 (A2A 서버, CLI, 테스트에서) 동작.
2. **Dynamic Prompting의 입력원** — 고객 등급·리스크 프로필이 context로 들어오므로 프롬프트가 상황에 맞게 조립됨.
3. **테스트 용이성** — 테스트에서 `BankingContext(llm_provider="none", …)` 주입만으로 LLM 없는 결정론 경로 강제 가능.

## 4. Mock 데이터 Enrich 계획

실전 확장을 가정해 시드 데이터를 다음과 같이 확장한다 (`seed.py` + 신규 테이블).

| 영역 | 현행 | 확장안 |
|------|------|--------|
| 사용자 | 1명 | **3명** (일반/VIP/리스크 고객 — Dynamic Prompting 시연용 등급·리스크 프로필 컬럼 추가) |
| 계좌 | 2개 | 사용자별 2~3개 + **외화/대출 계좌** (InquiryAgent 확장 여지) |
| 수신자 | 9명 | **20명+** — 동명이인 3쌍, 법인(전기/통신/보험), 경조사 그룹 |
| 이체 내역 | 12건/40일 | **120건+/6개월** — 월별 패턴(월세·관리비 반복), 시간대 패턴 → RecommendAgent의 통계 기반 추천 근거 |
| 정기이체 | 4건 | 8건 + 해지/실패 이력 |
| 사기탐지 룰 | 없음 | **신규**: 심야 고액, 신규 수신자 고액, 단시간 다건 등 룰 테이블 → SecurityAgent 데이터 기반 |
| 한도/수수료 | 코드 상수 | **정책 테이블화** (고객 등급별 한도·수수료 차등) |
| 사용자 선호 | 없음 | LangGraph **Store**에 저장되는 선호 메모리 (자주 쓰는 표현, 기본 출금계좌 등) |

## 6. 디렉토리 구조 (목표)

```
src/agents/
├── context.py                  # BankingContext (Runtime context_schema)
├── supervisor/                 # Leader Agent
│   ├── graph.py                # Planning → dispatch(Command/Send) → aggregate
│   ├── planner.py              # LLM 구조화 출력 ExecutionPlan
```
