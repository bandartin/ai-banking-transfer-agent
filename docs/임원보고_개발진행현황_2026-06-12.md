## 1. Executive Summary

현재 프로젝트는 **개인뱅킹 송금 업무를 자연어 기반 AI Agent로 처리하는 프로토타입**입니다. 사용자가 “엄마에게 5만원 보내줘”, “잔액 보여주고 자주 보내는 사람 추천해줘”처럼 자연스럽게 요청하면, 시스템이 의도를 파악하고 송금, 조회, 추천, 보안 판단을 역할별 Agent가 나누어 처리합니다.

이번 주에는 단순 챗봇이 아닌, 금융 업무에 필요한 **확인, 보안 판단, OTP, 수취인 모호성 해소, 실행 로그**를 포함한 Agent workflow 기반 구조를 구현했습니다. 특히 LLM이 송금 실행을 직접 결정하지 않고, 실제 금액 검증과 계좌 처리, 보안 판단은 결정론적 코드와 DB 트랜잭션으로 통제하도록 설계했습니다.

차주부터는 데모 수준을 넘어 실서비스 검토가 가능한 구조로 발전시키기 위해 **데이터 현실성, 보안 룰, 평가 자동화, 실행 로그 가시화, A2A 확장성**을 중심으로 고도화할 예정입니다.

## 3. 핵심 기술 구조

현재 시스템은 **Supervisor Agent가 전체 요청을 해석하고, 목적에 맞는 Sub-Agent에게 업무를 분배하는 구조**입니다.

```text
사용자 요청
   |
   v
Supervisor Agent
   |- TransferAgent: 송금 처리
   |- InquiryAgent: 잔액/이력 조회
   |- RecommendAgent: 자주 보내는 사람 추천
   `- SecurityAgent: 위험도/OTP 판단
```

### 기술적으로 중요한 포인트

| 기술 요소 | 적용 의미 |
|---|---|
| LangGraph workflow | 송금 업무를 단계별로 제어하여 확인, 보안, 실행 순서를 명확히 관리 |
| Supervisor/Sub-Agent 구조 | 업무 역할을 분리해 향후 상품 추천, 이상거래 탐지 등 신규 Agent 확장 가능 |
| Human-in-the-Loop | 송금 전 확인, OTP, 수취인 선택처럼 사용자가 반드시 개입해야 하는 지점을 명확히 처리 |
| Checkpointer | 대화 중간 상태를 저장해 “확인”, “수정”, “OTP 입력” 같은 멀티턴 흐름 유지 |
| Deterministic Service | 실제 송금 실행, 잔액 차감, 보안 룰 판단은 LLM이 아닌 검증 가능한 코드로 처리 |
| A2A 기반 구조 | 향후 Agent를 별도 서비스나 외부 Agent와 연동할 수 있는 기반 마련 |

핵심 방향은 **AI는 이해와 계획을 돕고, 금융 실행은 통제 가능한 시스템이 담당한다**는 것입니다. 이는 금융 서비스에서 필요한 안정성, 감사 가능성, 책임 소재를 확보하기 위한 구조입니다.

## 4. 주요 시나리오

### 4.1 기본 송금

사용자가 “엄마에게 5만원 보내줘”라고 입력하면 시스템은 수취인과 금액을 해석하고, 잔액과 보안 조건을 확인한 뒤 사용자에게 송금 확인을 요청합니다. 사용자가 확인하면 DB 트랜잭션을 통해 송금이 실행됩니다.

### 4.2 수취인 모호성 해소

“민수에게 보내줘”처럼 동일한 이름의 수취인이 여러 명일 경우 후보를 제시하고, 사용자가 선택하면 이후 같은 표현을 더 정확하게 해석할 수 있도록 별칭 메모리로 학습합니다.

### 4.3 금액 누락 및 수정

“지훈이한테 보내줘”처럼 금액이 빠진 경우 Agent가 추가 질문을 합니다. 또한 확인 단계에서 사용자가 “아니 3만원으로 바꿔줘”라고 말하면 기존 송금 흐름을 유지한 채 금액만 수정해 다시 확인합니다.

### 4.4 조회와 추천 병렬 처리

“잔액 보여주고 자주 보내는 사람 추천해줘”처럼 여러 목적이 섞인 요청은 조회 Agent와 추천 Agent가 동시에 처리하고, Supervisor가 결과를 취합해 하나의 응답으로 제공합니다.

### 4.5 고액 송금 보안

“집주인한테 400만원 보내줘”처럼 고액 송금 요청은 SecurityAgent가 위험도를 평가하고, 필요한 경우 OTP를 요구합니다. 이 과정은 LLM 판단이 아니라 명시적인 보안 룰과 고객 조건에 따라 처리됩니다.

## 5. 데이터 및 검증 현황

현재 데이터는 데모용 목업 데이터이지만, 실제 개인뱅킹 사용 패턴을 반영할 수 있도록 구성했습니다.

| 데이터 | 활용 목적 |
|---|---|
| 사용자/계좌 | 고객별 계좌, 잔액, 등급, 위험도 관리 |
| 수취인 | 가족, 친구, 임대인, 모임 등 개인 관계 기반 송금 |
| 이체 이력 | 최근 송금, 반복 패턴, 추천 근거 생성 |
| 즐겨찾기/별칭 | 자주 쓰는 표현과 수취인 매핑 |
| 정기이체 | 월세, 관리비, 회비 등 반복 송금 시나리오 |
| Agent 로그 | 실행 계획, Agent 호출, 보안 판단 근거 추적 |

검증은 현재 parsing, 송금 서비스, Agent 흐름, smoke test, A2A demo script를 중심으로 진행 중입니다. 차주에는 자연어 요청별 기대 결과를 정의한 평가셋을 추가해, Agent 선택과 보안 판단의 회귀 테스트를 강화할 계획입니다.

## 6. 현재 한계 및 리스크

| 영역 | 현재 한계 | 보완 방향 |
|---|---|---|
| 데이터 | 목업 데이터 중심으로 실제 거래 다양성 부족 | 사용자 유형, 거래 패턴, 실패 케이스 확장 |
| 보안 | 기본 금액/위험도 rule 중심 | 신규 수취인, 반복 송금, 시간대, 실패 이력 rule 추가 |
| 평가 | 자연어 발화별 정량 평가 부족 | Planner 평가셋과 회귀 테스트 구축 |
| 운영성 | 로컬 Flask/SQLite 중심 | 운영 DB, 로그 보존, 배포 구조 검토 |
| 관측성 | 실행 로그 기반은 있으나 관리자 관점 가시성 부족 | 판단 근거와 Agent 흐름을 화면에서 확인 가능하도록 개선 |
| A2A | 외부 Agent 연동 기반은 있으나 장기 실행 task 구조 미흡 | task id, status 조회, resume API 설계 |

## 7. 차주 진행 방향

차주는 기능을 단순히 늘리기보다, 현재 구조를 **검증 가능하고 설명 가능한 금융 Agent 구조**로 고도화하는 데 집중합니다.

| 우선순위 | 추진 항목 | 목표 |
|---:|---|---|
| 1 | Planner 평가셋 구축 | 자연어 요청에 대해 올바른 Agent가 선택되는지 자동 검증 |
| 2 | 보안 룰 고도화 | 고액, 신규 수취인, 반복 송금, 위험 고객 조건 강화 |
| 3 | 목업 데이터 확장 | 실제 개인뱅킹에 가까운 거래 패턴과 실패 케이스 확보 |
| 4 | Agent 로그 화면 개선 | Supervisor 계획, Agent 호출, OTP 판단 근거를 관리자에게 가시화 |
| 5 | A2A 구조 보강 | 외부 Agent 연동을 위한 task/status/resume 구조 설계 |

### 차주 예상 산출물

| 산출물 | 설명 |
|---|---|
| Planner 평가 데이터 | 발화별 의도, 필요 Agent, slot, 보안 여부 정의 |
| 보안 rule 확장안 | 신규 수취인, 고액, 반복 송금, 위험 고객 기준 정리 |
| 고도화된 seed 데이터 | 사용자 유형, 수취인 관계, 거래 이력, 실패 케이스 보강 |
| 관리자 로그 개선안 | Agent 판단 근거를 확인할 수 있는 화면/로그 구조 |
| A2A 확장 설계 | Agent 외부 연동을 위한 task lifecycle 초안 |

## 8. 결론

현재까지의 개발 결과는 자연어 송금 Agent의 핵심 업무 흐름과 기술 기반을 검증한 단계입니다. 특히 금융 업무 특성을 고려해 **LLM의 자유도를 제한하고, 실행과 보안은 통제 가능한 workflow와 서비스 코드로 처리하는 구조**를 확보했습니다.

차주에는 이 구조를 기반으로 데이터, 보안, 평가, 관측성을 강화해 임원 보고 및 후속 의사결정에 필요한 근거를 더 명확히 제시할 수 있도록 고도화하겠습니다.
